# Gemini 與 Claude Code 模型能力評分與時間分析（第一步）

這份分析整理了 Google Gemini 與 Anthropic Claude Code 在 2026 年 11 月的現役模型。資料來源包含本機 `agy` 與 `claude` CLI 實測支援清單，以及公開基準測試數據。

一個關鍵的前提是，兩家模型都支援可調式的思考深度（Gemini 的 `low / medium / high / xhigh`，以及 Claude Code 的 `--effort low / medium / high / xhigh / max`）。同一個模型開低思考與開高思考，執行時間可以相差 5 到 10 倍。

---

## 一、全模型精準評分表（滿分 10 分）

評分維度說明：
- **規劃推理**：需求拆解、系統架構設計、跨系統風險預判。
- **寫碼實作**：依照規格產出正確程式碼、重構與補測試的準度。
- **除錯定位**：從 log、DB 狀態與程式碼追出真正根因的能力。
- **審查抓漏**：當 PR reviewer 時找出邊界條件、安全漏洞與邏輯瑕疵的能力。
- **工具長鏈**：多步驟呼叫工具、讀多檔、不中途迷失方向的穩定度。
- **回應速度**：延遲越低、輸出越快，分數越高（10 分為秒級回應，1 分為數分鐘級等待）。

## 三、各模型優劣勢與適用場景

### Google Gemini 系列

#### 1. Gemini 4 Carbon
- **優勢**：深層推理與假設驗證能力極強，能主動考慮邊界條件、並發問題與資安風險，不容易寫出表面過關但底層有洞的解法。
- **劣勢**：`high` 模式下 TTFT 可達兩分半以上，拿來做一般 CRUD 或小修會感覺系統卡住；配額消耗也高。
- **適用場景**：
  - 高風險架構設計與資料庫 schema 重大異動規劃
  - 跨服務、難以重現的疑難雜症除錯
  - 高風險 PR 的最後把關審查（例如權限、金流、資料一致性）
- **不適用場景**：日常小 bug 修復、文件更新、需要快速來回對話的探索。

#### 2. Gemini 4 Argon
- **優勢**：在保持接近 Carbon 的工程推理深度下，首字延遲縮短到 Carbon 的三分之一左右，思考 token 較節制。
- **劣勢**：速度還是不如 Hydrogen，在簡單任務上性價比不高。
- **適用場景**：
  - 中大型功能開發的技術規劃
  - 需要系統性讀懂多個模組才能下手的重構
  - 正式 ticket 的跨模型對審（當需要比 Hydrogen 更嚴謹的視角，又不想等 Carbon 等太久時）

#### 3. Gemini 4 Hydrogen
- **優勢**：輸出速度約 190 tokens/s，比 3.8 Flash 快 2.5 倍，而且從 Carbon 適配而來，寫碼與工具呼叫準度很高。四段思考等級讓它能從秒級回應一路覆蓋到高難度執行。
- **劣勢**：在 `low` 模式下不適合複雜重構，容易漏看遠處檔案的相依性；需要跨多模組做全域架構決策時，還是不如 Carbon 與 Argon 穩。
- **適用場景**：
  - **`low / medium`**：改單一檔案、補單元測試、改設定檔、跑腳本、查資料。
  - **`high`（預設）**：絕大多數日常 ticket 實作、標準 bug fix、一般 PR review。
  - **`xhigh`**：較複雜的實作與除錯，不想切換模型但需要更深思考時。

#### 4. Gemini 3.1 Flash Lite
- **優勢**：極低延遲與極低成本，幾秒內完成。
- **劣勢**：多步推理與程式碼品質明顯較弱。
- **適用場景**：純文字分類、格式轉換、大量檔案的簡單規則檢查。

### Anthropic Claude Code 系列

#### 1. Claude Fable 5.2
- **優勢**：在多步推理與長週期 agentic coding 上表現最強，對模糊需求的拆解與防呆考慮最周全。
- **劣勢**：單價最高（輸入 $8 / 輸出 $40 per 1M tokens），且高 effort 下等待時間長，日常任務使用大材小用。
- **適用場景**：
  - 跨多個 repo 的複雜系統設計與遷移規劃
  - Opus 5.5 或 Carbon 解不開的死鎖或深層 bug
  - 關鍵基礎設施與核心規則的架構審查

#### 2. Claude Opus 5.5
- **優勢**：長週期寫碼極穩定，對程式碼風格、上下文一致性與工程規範的遵循度極高，是 Anthropic 官方建議的預設主力。
- **劣勢**：比 Sonnet 5.5 貴一倍且慢一些，拿來做重複性高或範圍很小的修改不划算。
- **適用場景**：
  - 正式業務 ticket 的規劃與主力實作
  - 跨檔案重構與複雜測試補齊
  - 雙模型共識機制中的主力審查方（跟 Gemini 4 Hydrogen/Argon 互審）

#### 3. Claude Sonnet 5.5
- **優勢**：速度明顯快於 Opus，寫碼與除錯能力卻依然強悍，來回互動體感流暢，成本只有 Opus 一半。
- **劣勢**：面對極度複雜的隱晦 bug 或超長跨度架構規劃時，深度略遜於 Opus 與 Fable。
- **適用場景**：
  - 規格已經寫清楚的功能實作與前端/腳本開發
  - 日常 PR 的快速預審與第一輪抓漏
  - 需要快速驗證想法的原型開發

#### 4. Claude Haiku 5.5
- **優勢**：極速且幾乎沒有成本壓力，適合高併發或當作前置過濾器。
- **劣勢**：不適合獨立處理需要深層上下文理解的寫碼任務。
- **適用場景**：
  - 新 ticket 進來時的第一步自動分類與模型分派判斷
  - 讀取大量 log 做初步過濾、摘要與關鍵字提取
  - 單純的文案、翻譯或設定檔小改

## 四、給第二步（建立自動路由規則）的初步對應建議

為了避免「簡單事等太久，難事用錯模型改壞」，後續第二步可以把任務切成三個階段來對應不同頻段：

1. **前置分派（Router / 1 到 5 秒）**：用 `Haiku 5.5` 或 `Hydrogen (low)` 根據 ticket 複雜度、影響範圍與風險等級決定後續三個角色要用誰。
2. **規劃階段（Planner）**：
   - 簡單或範圍明確：直接由 `Hydrogen (high)` 或 `Sonnet 5.5` 規劃並執行，不額外拆段。
   - 中高難度跨模組：`Opus 5.5` 或 `Gemini 4 Argon`。
   - 高風險核心架構：`Claude Fable 5.2` 或 `Gemini 4 Carbon`。
3. **執行階段（Executor）**：
   - 快速小改與補測試：`Gemini 4 Hydrogen (low/medium)` 或 `Sonnet 5.5`。
   - 一般正式開發：`Gemini 4 Hydrogen (high)` 或 `Opus 5.5`。
4. **檢測審查階段（Reviewer / Consensus）**：
   - 維持雙異質模型互審原則（`claude` 與 `gemini` 交叉）。
   - 一般 PR：實作方與 `Sonnet 5.5` / `Hydrogen (high)` 互審。
   - 高風險或核心系統 PR：`Opus 5.5` 與 `Argon` / `Carbon` 互審。
