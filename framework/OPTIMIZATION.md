# Optimization Playbook — 把既有服務改快，並讓舊路退場

> 什麼時候讀：被指派「讓某個服務/端點變快」、「拿掉中間那一層」、「退役一組舊路由」。
> 來源：一次完整走完的 optimization + retirement program（兩個 NestJS 服務、三層
> pass-through proxy、8 個 PR、四個端點達標、13 條路由排期移除）。每條規則都對應那次
> 實際踩到或救到的事，不是推論出來的。
> 通則紀律在 `ENGINEERING-LESSONS.md`；本檔只放「優化／退場」這條路徑上的**順序與判準**。

## 單一主張

慢的那一段，通常不是你最容易改的那一段；而能不能刪掉舊路，取決於你能不能**量出**沒人在用，
不是**推出**沒人在用。整個工作的成本重心在證據，不在程式碼——實測的分布是：
切換本身一天，證明與公告九天。預算要照這個比例編。

---

## Phase 0 — 地面（動任何一行之前）

沒有這四件事，後面每個數字都可能是假的。

1. **同步並釘住 ref**。每個會碰到的 repo `git fetch` + 確認沒有 behind/diverged。
   **派出去的每個 subagent 都要收到明確的 ref，不能只給路徑**——它們讀的是同一份工作樹，
   落後的樹會讓你以為拿到了第二個人的獨立確認。
2. **測試先修到全綠**（各 repo 一個 test-baseline PR，只動測試）。之後任何紅燈都只能是你造成的；
   沒做這步，你會把每一次紅燈都花在證明「這本來就壞了」。
3. **校準量測工具**。在信任任何查詢之前，用一個**必然存在**的值跑一次同樣的查詢。
   常見的靜默失真見下方〈量測工具的坑〉。
4. **記下 baseline**：關鍵端點的 p50/p95/錯誤率/每小時流量，以及一條代表性 trace 的逐段耗時。
   baseline 要**寫進檔案**，不是留在對話裡——你會需要在兩週後回答「本來是多少」。

## Phase 1 — 找到真正的瓶頸

- **關鍵路徑，不是單跳**。把一個 request 畫成 serial／parallel 結構，只有最長那條鏈影響 p95。
  一次實測：一個「移除一跳 proxy」的改動每次省 25 ms、比對 7,702 筆 99.99% 相同——
  **完全正確，而且對 p95 毫無影響**，因為尾巴屬於另外兩個下游服務。
- **計畫裡的每一條「事實」都要重驗**。用現行 code（釘住的 ref）+ 一筆**新抓的** trace。
  同一次 program，讀碼分析推翻了計畫四個前提中的三個。前提來自會議記錄、ticket、
  或你自己上週的筆記時，一律當作二手資料。
- **每個候選都要寫成可否證的句子**：「改完 p50 會從 X 降到 Y，因為關鍵路徑上少了 Z」。
  寫不出這句，代表你還沒找到瓶頸，不代表這個改動不值得做。
  事後說「我早知道那個沒用」沒有價值；事前寫下來才有。
- **瓶頸在別人家時要講出來**。trans-side 能做的優化有上限；把「這段屬於哪個團隊」寫進分析，
  讓要不要開跨團隊 ticket 成為一個明示的決定。

## Phase 2 — 改法的排序

由便宜安全到昂貴危險，同一個端點通常照這個順序吃：

| 類別 | 典型收益 | 風險輪廓 | 需要的證據 |
|---|---|---|---|
| 排程（把序列改並行、提前發送、不要在 `Promise.all` 的陣列字面量裡 `await`） | 中 | 低，但會改變失敗時的副作用順序 | golden spec 含每個下游的失敗案例 |
| 連線重用（per-message connect/disconnect → 共用 producer/client） | 高 | 低 | 送出的訊息數與順序不變 |
| 預取（只依賴少數參數的下游，提前發、原位置 await） | 中高 | 低 | 同上 + 原本的 catch 行為保持 |
| 去掉一跳（proxy/公開 ingress → 直連叢集內） | 低到中 | 中，授權行為可能不同 | 兩條路的授權與回應形狀逐項對過 |
| 批次 RPC | 高 | 中高，join 語意與錯誤欄位不同 | shadow 比對 |
| 換下游端點 | 高 | 高，回應形狀常常不同 | shadow + 明確的語意決策 |

**先查授權對稱性**：兩條路的 guard 常常不同（有的有 ownership gate、有的只有 JWT）。
「改直連會不會失去任何授權行為」必須逐條回答，不能整組回答。

## Phase 3 — 零行為變更的施工

- **golden spec 先行**，而且要**釘住每個階段的失敗與降級路徑**，不是只釘 happy path。
  並行化改變的正是「某個下游失敗時，其他副作用有沒有發生」。實測救過一次：
  naive 版把某個呼叫移進第一波，golden 的降級案例立刻抓到一個欄位不再被寫入。
- **三段式開關**：`off`（逐位元組等於今天，預設）/ `shadow`（兩邊都跑、**回舊的答案**、記差異）/ `on`。
  部署那天行為不變，之後每一步是**改設定**不是重新部署。這是整套流程裡唯一真正奏效的設計。
- **不要寫會成功的預設值**。跨環境的預設值最糟——它不會報錯，會安靜地連到另一個環境。
  缺設定時一律退回舊路；啟用新路要**兩個刻意動作**（填位址 + 開模式），不能只要一個。
- **shadow 的比對邏輯是最該 review 的部分**。先正規化掉「不是差異的差異」
  （absent vs `undefined`、absent vs 空陣列、數字 vs 數字字串），否則它每次都喊不一致，
  然後沒有人會再看它。差異報告只帶**路徑與型別，不帶值**——那是別人的資料。
- **歸因誠實**：接手別人的呼叫時，service-name 之類的標籤要填**真正在呼叫的服務**，
  那是歸因不是授權。並把這個刻意差異寫進 PR。

## Phase 4 — 部署與驗證

- **merge ≠ 上線**。看跑著的 image SHA，必要時 exec 進去 grep 本次變更的字串。
  同一個 program 踩到兩次「以為上線了」。
- **rolling 完成的判準是新實例本身**：`rollout status` 回報成功時舊實例可能還在、還帶舊設定。
  判準是「只剩新的 replicaset」+ 逐個實例讀環境變數。
- **在部署產物上實跑保護邏輯**。把 dist 裡那支檔案載進去，餵空值進去，確認它真的退回安全模式——
  單元測試綠燈不是部署驗證。
- **量測窗要乾淨**：注意同期別人的部署會汙染比較（一次比較必須在某個時間點截斷，
  因為另一個人的改動在那時上線）；比可比的時段（業務時間 vs 離峰）；
  **單一對照期不足以判定個位數百分比的差異**——先確認新舊數字都落在既有基準線的哪一側。
- **auto-deploy 會繞過你的節奏**。「先 staging 後 prod」靠的是紀律，隨時會被別人的一次 merge 打斷；
  真正在守門的是 Phase 3 那個「缺設定就不動」的預設值。

## Phase 5 — 退場（刪掉舊路）

技術上最簡單、成本最高的一段。順序不能換：

1. **先補歸因**。沒有 caller 紀錄之前，「沒人在用」只是 code search 推論，看不到瀏覽器、
   外部系統、和你沒 clone 的 repo。補上之後同一個結論的強度差一個數量級
   （一次實測：推論「10 條沒人用」→ 量到「2,936 : 0」）。
2. **零流量要有對照組**。同一條查詢、同一份資料來源，去數一個**必然存在**的值；
   數得到，那個 0 才是 0。
3. **逐條找替代品並驗證形狀**。「都呼叫同一個 service」不等於 drop-in：
   實測 13 條裡有 2 條回應形狀不同（一條回壓縮串流 vs 解析後的 JSON、一條定範圍機制不同）。
   同時明確列出**要留下什麼**——共用的 service 與其設定 key 通常不能刪，新路正走在上面。
4. **公告一次講完**。分兩次公告等於邀請第二輪「沒人通知我」。內容要有：連到哪、改成什麼、
   最後期限，以及**會咬人的差異**（例如新路多要一個參數，沒帶就失敗）。
5. **把等待變成排程**，並把合約寫死：量到真零才開 ticket + draft PR；任何流量、工具失敗、
   或對照組沒回資料 → 什麼都不開、只報告。失敗的執行不寫 marker，才會再響一次。
6. **共用文件一律「先讀當前版本、在其上改、帶 version 送出」**。同一個帳號的編輯在版本紀錄裡
   分不出是人是 agent，覆蓋掉別人的修改看不出來。

## 量測工具的坑（先校準，不然整段分析是假的）

- **自己拼的查詢回零筆**：先用必然存在的值驗證那條查詢本身。
- **全文搜尋 vs 屬性欄位**：路由字串常在結構化屬性裡，free-text 搜不到不代表沒有流量。
- **stdout ≠ 全部日誌**：走結構化 logger 的事件不進容器標準輸出；在 pod 裡 grep 得到 0
  不代表沒發生。同一個 program 因此錯了兩次。
- **URL 含 query string**：直接 GROUP BY 會炸成上萬列並被截斷，要先截到 `?` 前面。
- **聚合器的語法錯誤會靜默降級**成另一個查詢；`avg of percentiles` 是近似值，不是 p95。
- **工具掛掉時改從來源證**（服務自己的日誌），不要盲目重試——但要講清楚來源的時間窗更短。

## 收尾檢查表

- [ ] 每個 repo 都 fetch 過且確認不落後；subagent 都拿到釘住的 ref
- [ ] 測試基準綠、baseline 數字寫進檔案
- [ ] 每個改動都有事前寫下的可否證預估，事後逐項對過
- [ ] 每個危險切換都有三段 mode，且缺設定時退回舊路
- [ ] golden spec 含每個下游的失敗案例
- [ ] 部署後在**部署產物**上驗過保護邏輯，且確認跑的是新 image
- [ ] 退場前補了歸因、零流量有對照組、替代品逐條驗過形狀
- [ ] 公告一次講完、含期限與不相容差異；等待期有排程接手
- [ ] 報告裡每個結論都標了「量到 / 推得 / 假設」

## 反模式（都實際發生過）

- **拿舊樹當現況**：`fetch` 是動作，「同步」是判斷；`[behind N]` 常常就印在你自己那一次指令的輸出裡。
- **用錯誤的前提去更正一個正確的說法**：改口跟說話要求同樣的證據強度。
- **把「順手數到的另一個 0」當第二佐證**：先確認那個計數器真的會記錄你要的事。
- **為了保險放寬條件**：清理與比對的範圍要綁當次操作，不要「順便也看看」。
- **把演練過當成驗證過**：回滾流程只在測試環境演練過，就不要說它「可用」。
