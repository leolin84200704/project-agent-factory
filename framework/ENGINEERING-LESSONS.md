# Engineering Lessons — 通用工程紀律

> 從真實事故蒸餾的跨專案通則。每條都對應至少一次實際踩雷。
> 動 DB / 部署 / prod / migration 前先掃過對應章節。
> 新教訓寫入規則見 `RETRIEVAL.md` § Write-back：確定可泛化才進這裡，job-specific 留在該 instance 的 LTM。
> 條目格式、字數上限（≤50 字）與 Add/Modify/Deprecate 生命週期見 `../CONTRIBUTING.md` § Lesson PR 規格。

## 驗證紀律

- **Test before push** — 會影響 prod 的 push 前必跑 unit test，且涵蓋新 logic 的每個分支。compile pass ≠ behavior correct。
- **Verified means live, not mock** — 別把 mock unit test 說成「線上驗證」。prod 行為的結論要用真實 DB / 部署中的 service 重現。
- **Verify peer-observed state** — 修 network/lifecycle 問題時，驗證對端可觀察的狀態（對方的 session count、connection 數），不只看自己這邊的 log。
- **Rolling deploy 完成的判準是新 pod 本身，不是 deployment 聚合欄位** — k8s rolling update 期間 `deployment.status.readyReplicas` 計入**舊** pod，所以「spec image 已更新 + ready≥1」會在新 pod 還沒起來時就成立，是假完成訊號；照它開跑驗證會打到舊版 code，測試結果全部作廢。正確判準：存在一個 **image == 目標版本** 且 `containerStatuses[].ready==true` 的 pod（必要時再確認舊 pod 已終止）；最終確認 = **exec 進 pod 驗證編譯產物內容**（grep 本次變更的具體字串）——tag/ready 都對不代表跑的是新 code，同日兩次假陽性都是靠 content 驗證擋下。同理適用任何滾動替換系統：完成訊號要綁「新實例的身份+就緒」，不能用會混入舊實例的聚合計數。旁註：切換過程中單次 API 讀值可能出現 transient 異常值，關鍵判斷要重讀確認、不要憑單次讀值行動。
- **並發 merge 會讓舊 build 蓋掉新 artifact — 收尾要驗 serving 版本身分** — per-commit 觸發的 CI/CD 有個 race：兩個 PR 相隔很近 merge，會觸發重疊的 build，較早 commit 的 build 可能**最後**完成，把新 commit 的 image/artifact 蓋回舊 code。「build 綠燈」≠「新 code 正在服務」。根因是 build 之間無 commit-ordering 保證、deploy 又是「最後完成者勝」。連續 merge（尤其打同一條 pipeline 的兩個 PR）後，必須驗證實際 serving 的 revision/image digest 對得上目標 commit，而不是只看最後一次 build 回綠。這是上一條 rolling-deploy 教訓的姊妹：兩者都要求收尾時綁定「正在服務的 artifact 身分」，而非任何聚合或「已觸發」訊號。
- **Batch DB verify 100%** — 批次 INSERT/UPDATE 後驗證全部 rows，絕不抽查。
- **JOIN scope reverse audit** — prod UPDATE-WHERE-JOIN 跑完後，用更廣的 criterion 反向 SELECT 找漏網 row；SQL 的 `NULL = NULL` 是 false，會靜默漏掉。
- **盤點缺漏要對「應有全集」，不要從錯誤 log 反推** — 查「少了哪些」時先建應有集合（上游 feed / 排程表 / 型錄）再 diff 實有產出；錯誤 log 只記系統知道的失敗，crash、race 蓋寫、靜默丟棄都不在裡面。適用: 任何「缺了一筆/一集/一單」的 triage，以及 backfill 後驗證完整性時。
- **End-to-end equivalence before swap** — 替換 RPC/service 實作前，diff 前後 output 完全相同；proto 相同 ≠ marshalling 相同。
- **Channel liveness is third-party state — round-trip test it** — user-facing 通道（chat bot、webhook 推播、訂閱）的關鍵狀態存在第三方且可被外部行為者改寫；「己方註冊/發送動作執行成功」≠ 通道活著。deploy/驗收收尾必做一次真實 round-trip（實際收發各一則並確認）；長期監控要查第三方的實際狀態（如 getWebhookInfo）而非自己的 log，drift 要自癒並通知用戶。同一通道故障被用戶發現兩次 = 缺的是測試不是修復。
- **資料違反現行設定 ≠ engine bug — 先為設定變更定年** — 當存量資料看起來違反現行設定（預約落在可用時段之外、記錄超出現行 quota、舊值過不了現行 validation），第一個要排除的假設是「設定在資料寫入之後被改過」：先確認寫入當時生效的設定，再開始懷疑驗證引擎。設定 store 常沒有歷史（無 updated_at、無 audit log），但 delete-and-recreate 的儲存模式讓 surrogate key 順序成為可用的定年工具——某物件的整組 row id 若是全表最高，即證明它是最近被整批重寫的，可與資料寫入時間交叉比對出先後。反向教訓：任何 user 可自行編輯、又被引擎當驗證依據的設定表，要有 updated_at 或 audit，否則 triage 只能靠 id 推理，且縮小設定時應偵測並提示落在新設定之外的既有資料。
- **安靜的觀測窗不是故障證據 — 要量輸入端** — 「改完後 N 分鐘沒有預期產出」不能推論成壞了；必須先確認那段時間**輸入是否真的到達**。event-driven 系統的正確量法：topic/queue 的 offsets-by-timestamp（該窗內生產了幾筆）+ consumer group lag；**lag ≈ 0 代表系統把能拿的都吃了 = 健康且輸入為空**，跟「卡住」是完全相反的結論。真實事故（2026-07-31）：cutover 後 61 分鐘零產出，我判定失敗並回滾，實際上上游那小時就是沒有事件，事件在第 65 分鐘到達且新路徑處理正確——回滾反而造成 ~17 筆重複交付與 5 筆中斷的 in-flight 工作。配套兩條：(a) **看證據的時間戳，不只看數量**——「切換後有 64 筆事件」在確認每筆的到達時間之前毫無意義，那 64 筆全部在我量完零之後才到；(b) **檢查這個「故障」有沒有自己已經寫下來的替代解釋**——我先前才記錄過「這個系統有整小時零產出的自然空窗」，卻在自己的改動受嫌疑時忽略該 baseline。嚴謹的統計論證架在錯誤前提上，只會讓錯誤結論看起來更可信。
- **Log 平台的 severity 標籤是 pipeline 產物 — 先校準再下「無錯誤」結論** — 「`status:error` 查到零筆」不能推論成沒有錯誤：service 的 error log 進到集中平台（Datadog 等）時，severity 是由 ingest pipeline 對映的，沒設 remap 的 service 其 level-50/ERROR log 會整批落在 `status:info`，用 severity facet 過濾永遠是空的。真實案例（2026-08-10 VP-17651）：engine 一週內 500+ 筆 pool-exhaustion 500 全掛在 status:info，owner 用 status:error 查是乾淨的，P1 靠客戶回報才發現。硬規則：對不熟的 service 下「log 沒有錯誤」結論前，先**校準**——找一筆已知確實發生過的錯誤（一個 5xx、一次 exception），確認它在平台裡的實際標籤/欄位，再用那個欄位（`@err.type`、`@res.statusCode`、raw message pattern）當查詢鍵；校準失敗 = 你的查詢鍵錯了，不是系統健康。姊妹規則：瀏覽器端被擋的請求（CORS preflight 拒絕）在 server 只留一筆正常 OPTIONS 204，**任何** server log 都不會有錯誤——「server log 乾淨 + 用戶持續失敗」的組合要主動想到 client-side 失敗類，discriminator 是用戶的 DevTools Network/Console 截圖，不是更多 server log。
- **「未設定」有多種物理形態 — 寫 settings fallback 前先量測 unset 的真實形狀** — 「設定有值→用它；未設→fallback/報錯」這類邏輯裡，「未設」在儲存層常不只一種形態：完全沒有 row、有 row 但值為空字串、值為字面 `'null'`/`'undefined'`、row 存在但 inactive flag 關閉。用「有沒有 row」當判準會把空值 row 誤判成已設定。正確做法：coding 前對 ground truth 量測各形態的分佈（一次 GROUP BY 就夠），並向既有 reader 的實作對齊語意（現行讀取端把什麼當 unset，你就把什麼當 unset）。真實案例：某 clinic 級設定全量量測結果為 37% 可用值 / 37% 空字串 row / 26% 無 row——空值 row 跟可用值一樣多，而該設定的既有 reader 以 `value || null` 處理，證實空字串=未設是系統既定語意；live 讀取 API 對「未設」的 clinic 回的也是 `{value:'', isActive:true}` 而非空集合。
- **Read the helper before you build on it — stubs log success** — 依賴既有 helper/service method 前先讀它的實作，不能只看名字和回傳型別。真實案例：SFTP `moveFile()` 是空 stub — `ensureConnected()` 後直接 log "File moved successfully" 回 `{success:true}`，從未呼叫 client，任何 caller 都拿到假成功且無錯誤可觀察。判斷法：宣稱有副作用的 method 內若沒有對應的 client/IO 呼叫即是 stub；接手時先補真實作（含 timeout）+ 行為級 unit test，再開始建上層功能。
- **對非決定性元件下「在退化」結論前，先量同一輸入的重複變異** — 固定同一份輸入重跑 N 次先建立變異帶，再判斷新樣本是否落在帶外；跨樣本單點串成的趨勢線分不出退化與雜訊，而「換掉它症狀就沒了」也只證明兩個元件不同。適用: 判斷模型/供應商換版是否退步、監控生成式輸出品質、設輸出量（長度/分數/count）的 guard 與告警閾值時。
- **Validate the grader before believing a regression** — 評測出現 0%/100% 等極端值時，先用一個已知正確的答案回灌，確認判定條件**可被滿足**，再懷疑受測系統。適用: 自動化 grader、CI 斷言、監控閾值——任何判定邏輯與受測對象分離的量測。判定條件若是設定檔裡的 pattern，特別要查解析路徑（無依賴時的 fallback parser 常靜默吃掉跳脫字元，使 pattern 恆不命中）；並保留失敗當下的原始輸出，否則「不可評分 / 真的答錯 / 不穩定」三者事後無法分辨。
- **會 fail-open 的 gate 要計數 — 沒有計數器的 gate，實際覆蓋率是未知數** — 品質/安全 gate（LLM-as-judge、驗證器、風控檢查）遇到自身依賴故障時 default-allow 是**對的設計**（不能讓一次 503 掐死所有輸出），但 fail-open 若只留一行 WARN，「gate 放行了 100 筆」與「gate 今天整天是關的」在 log 上長得一樣，而後者代表那段時間的產出**完全沒被檢查過**。硬規則：每條 default-allow 路徑要有自己的計數器（fail-open 次數 / 佔比），超過閾值就告警；`gate_passed` 與 `gate_unavailable` 必須是兩個不同的結果值，不能都記成通過。判斷這條路徑罕不罕見不能憑直覺——gate 通常掛在**與主流程同一個**不穩定依賴上（同一個 LLM 供應商、同一個外部 API），主流程忙 = 供應商過載 = gate 最可能失效的時刻，兩者是正相關不是獨立。適用: LLM-as-judge / 內容審核 / fact-check 驗證器 / feature-flag 預設放行 / 憑證服務不可用時的 allow-by-default。姊妹規則：上面的 stub 教訓是「機制根本沒在做事」，這條是「機制在做事但會靜默退場」，共同判準是**成功訊號要能區分「檢查過且通過」與「沒檢查」**。
- **錯誤事件出現與否不代表嚴重性 — 嚴重性要綁當輪的成功產出計數** — 有 retry / circuit breaker / 降級路徑的系統，「做完一部分才停」與「一筆都沒做成」會寫出一模一樣的錯誤行，用錯誤有沒有出現來 triage，會把 N 次良性降級和 1 次全滅混為一談。硬規則：每輪獨立記一個成功產出計數（persisted / delivered / committed 的**筆數**），triage 先讀它再讀錯誤訊息，計數為 0 才是事故；健康判準也綁它，不要綁 log 檔的 mtime——失敗訊息一樣會把 log 餵飽，「還在寫 log」與「還在工作」在 mtime 上長得一樣。適用: 批次作業、排程 job、含 retry 或 breaker 的 pipeline，以及任何「錯誤是常態、全滅才是事故」的系統。
- **中介層自報的失敗原因是猜測，不是量測** — breaker/retry/wrapper 印出的原因字串不算證據；根因要逐筆撈每次失敗**自身**的簽名欄位，再用一次同路徑 live probe 排除「永久性故障」整條分支。適用: 批次全滅、疑似額度/配額耗盡、任何由中介層代述失敗原因的系統。

## 變更範圍紀律

- **Config coupled with code** — 新增任何 `process.env.X`（或等價設定），同一個變更裡就更新所有部署 config（yaml/ConfigMap），並明說改了哪些。
- **Schema migration before deploy** — 對非 ORM-managed 的 prod DB，schema 加欄位必須先手動 ALTER 到 prod 才部署，否則整個 model 的讀取會全數失敗。
- **Audit callers when adding fallback** — 加 fallback 機制時，同一個 PR audit 並遷移所有同類 caller；revert 一個 service 時 audit 同 server 其他同類風險。
- **Sync sibling encodings of an invariant** — 改一個值/邊界的語意時，同 function 內所有衍生點（顯示、驗證、查詢窗、search 邊界）要用 single source 一起改；測試別 mock 掉共用路徑（假綠燈）。
- **Migrate all readers, no mirror** — 替換 source-of-truth 時，遷移所有 reader（含 generic DTO mapper）然後停寫舊 store；「先雙寫留 mirror」只會 diverge。
- **Rollback 是有 blast radius 的變更，不是免費的還原鍵** — 「照 runbook 回滾」聽起來安全，但回滾本身會產生副作用，決策時要跟「維持現狀」一起評估。最常見的形態：**consumer group 切換**。A→B 切換期間 group A 停止消費、offset 停在切換點；切回 A 就從那個 offset 重放，下游若沒有 idempotency gate 就是**重複交付**（重複寫入若是覆寫同一列，row count 還會看起來乾乾淨淨，指標騙人）。硬規則：任一方向切換前，先把**目標 group 的 committed offset 推到 high watermark**（`admin.setOffsets`），或明確接受重放。真實案例：回滾重放 1,940 筆造成 ~17 筆重複；切回去前若不先推 offset，另有 8,501 筆待重放。另一個副作用：**重啟會殺掉 in-flight 的 job**（BullMQ 等），留下 `next_retry_at=null` 的孤兒列，不會自癒，必須事後逐筆補跑並驗證。
- **大改動拆成至少 3 個 commit，切在 revert 邊界上** — 一個把新元件、接線、infra/config 全塞在一起的肥 commit，無法只 revert 有風險的那一片（k8s manifest / prod config），要退就得連安全的部分（新 service + 測試）一起退。寫 code **之前**就規劃邊界：(1) 新能力 + 其單元測試（未接線、inert）→ (2) 接進呼叫端（真正的行為改變）→ (3) infra/config/依賴（最難 revert 的放最後且獨立）。附帶約束：branch 一旦 push，回頭拆需要改寫歷史，而 force-push 在工作 repo 是禁止的——所以要嘛一次切對，要嘛用新 branch 重建。
- **Capability flag enables a pipeline** — backfill 或開 flag 前，確認下游 pipeline 的相依 config 都在，否則 flag 開了功能還是斷的。

## 設計判斷

- **Diagnosis in the agent layer, facts in the app** — 系統有 LLM agent 常駐監看時，失敗「診斷」（根因推理、跨表反查、修法建議）放 agent 層：偵測到失敗後由 agent 查證並把英文結論寫回 DB 的 detail 欄位；app code 只記錄裸事實（錯誤碼、上游回應）並提供可寫欄位。診斷邏輯寫進 app 會讓每個新失敗型態都變成一次 code deploy，而 agent 層改 prompt 就能涵蓋。配套硬規則：短 TTL 的證據（container log 會被下一次 redeploy 洗掉）必須由 agent 在**偵測當下**快照到耐久儲存（repo/檔案），不能等事後查——事後永遠查不到。
- **Prefer stable id over name matching** — 有 unique id 可用時不要用 display name 做 matching key，主動建議改用 id。
- **關鍵依賴別綁移動標籤，且要對輸出形狀下量化斷言** — `-latest`/`:latest`/`-preview`/浮動版號會原地換版、無版本紀錄，行為在腳下改變且不報錯；pin 只擋掉一種漂移（preview/exp 通道自己也會換版），真正的防線是對產出下量化 guard + 告警。適用: 接第三方模型、image tag、外部 API 版本時。
- **Owner-scoped, not actor** — 解析 per-owner 屬性（timezone、settings）要用資源擁有者的 id，不是 JWT actor 的；admin 代操作會打破 actor lookup。
- **Cleanup filter scope** — prod DELETE 的 WHERE 必須綁定當次操作範圍（時間 + 明確 ID），絕不為「保險」放寬 filter。
- **No overgeneralize from single case** — 寫通則前 grep 多個 case 確認真正原因，別從單一 case 反推普遍規則。
- **Headless LLM CLI 預設載入整個 harness context** — 用 agent CLI 的 headless/print 模式（如 `claude -p`）當純文字 worker 時，它預設會把整個工具 schema、所有 MCP server、專案 memory 檔、動態 system prompt 都塞進 context——實測連一個字的 prompt 也可能 ~170K token/call，其中工具 schema 是最大宗（非 MCP）。純文字進、JSON 出、不呼叫任何 tool 的任務要明確關掉：`--tools none` + 空 MCP config + 極簡 system prompt + 關動態 section，可降 ~30×。別假設 headless 模式就是精簡的；用 `--output-format json` 看 `usage` 逐項驗證哪個開關真正省 token。
- **重跑判準要綁產物，不是綁通道** — HTTP-trigger 的 cron/scheduler job 跑超過 caller 的 attempt deadline 會被視為失敗而重試，重試與仍在跑的原請求**並行** = 你沒設計過的併發（重複工作、狀態互蓋）；同一缺陷還有第二種形態：wrapper 只用 exit code / stdout 有無錯誤字串判定成敗，於是「工作已完成、只是回傳途中斷線」被誤判成失敗而**整輪重跑**（false red）。把 deadline 設 ≥ handler 最長執行時間只擋得住前者。硬規則：重跑前先查該輪**產物**是否已落盤（輸出檔存在 / commit 已進 / 狀態列已 terminal），產物在就視為成功；並假設 retry 遲早會在成功之後誤觸發一次，所以可被重跑的工作必須 idempotent。這是「嚴重性要綁成功產出計數」那條的鏡像——同樣是拿通道狀態當工作狀態的代理，一個方向漏看事故（false green），另一個方向重做已完成的工作（false red，代價是重複副作用與白燒配額）。適用: 設定 scheduler 觸發長任務時；發現同一 job 有兩份並行執行紀錄時；長任務在收尾附近斷線時。
- **Idempotency key 不可被 terminal failure 消耗** — 「先插 unique row 再處理」是正確的併發防護，但 resend 分支必須看既有 row 的**狀態**再決定：處理中/已成功 → 短路回 duplicate；terminal failure（驗證失敗、拒絕、下游錯誤）→ 用 status-gated 原子 UPDATE reclaim 該 row 重跑（N 個併發 resend 恰一個搶到）。否則「修正問題後重送同 key」這個 idempotency 的核心使用情境永遠走不通，且呼叫端拿到的 5xx「可重試」承諾是假的。配套：若 pipeline 是 charge-first / 先產生副作用再完成，副作用完成的**當下**就要把憑證（payment id 等）持久化到該 row，retry 時 replay 而非重做——不然 failed 狀態永遠不敢放開重試。Doc 寫了 retry 語意不代表 code 有實作，兩邊都要驗。
- **`void somePromise()` 丟棄的是回傳值，不是 rejection** — fire-and-forget 一個 promise 時，`void` 只讓 linter 閉嘴，不會註冊 rejection handler；該 promise 一旦 reject 就是 unhandled rejection，而現代 Node 預設**直接結束 process**。後果的方向常常是反的：一個「best-effort、失敗也不該影響主流程」的旁支（告警、通知、指標上報）反而成為讓整個服務掛掉的原因。硬規則：任何不 await 的 promise 都要顯式 `.catch()`；如果被呼叫的東西可能同步 throw（DI 給了 undefined、SDK 初始化未完成），再包一層 try/catch。旁證：同一個 codebase 早先就為另一條 fire-and-forget 的持久化呼叫補過 `.catch()`——說明這是會重複發生的形態，不是一次意外。附帶一條測試紀律：驗證「這個旁支失敗不會弄壞主流程」的測試要用**真的 rejected promise**（`mockRejectedValue`），不要只用同步 throw——前者才會暴露缺少 handler 的問題，而它的症狀是 test runner 整個 crash，不是一個 failing assertion。

- **從「自己算」改成「信上游的標籤」時，輸入定義域會無聲擴大 —— 別用列舉式 switch 接別人擁有的詞彙表** — 重寫/移植一個分類邏輯時，最容易漏掉的不是演算法而是**契約的方向改變**：舊實作拿原始值自己推導分類（定義域 = 值域，封閉），新實作改成信任上游預先算好的標籤（定義域 = 上游的整個詞彙表，而那個詞彙表由別的團隊擁有、會長大）。此時若照著「線上看過哪些值」寫成 `switch`，漏掉的分支不會是空值或例外，而是**被 default 分支吞掉並轉成錯誤語意**——正常結果被標成失敗、合法代碼被拒。兩個實際形態：(a) 結果推送的分類標籤多了一族「超出可測範圍」前綴（`OUT_OF_*`），switch 沒有該 case，正常值一路掉進 `UNKNOWN_ERROR`，對外交付的訊息變成「此項未執行」；(b) 訂單 API 的代碼白名單只認得舊命名的前綴，型錄新增的外部代碼一律 422 拒絕。判斷法與對策：**先問這個詞彙表是誰定義的**；不是自己定義就別列舉，改用結構化正規化（剝掉已知的修飾前綴/後綴再比對基底），並且**保留大聲的 fallback**——default 分支的 ERROR log 往往是這類 bug 唯一的可見性來源，把它改安靜等於讓下一次靜默誤分類永遠不被發現。反向查核也便宜：同一個詞彙表通常有多個消費者，grep 其他 repo 怎麼處理同一個標籤，比去問人快且更可靠（三個獨立消費端一致把前綴當註記、把後綴當分類，就是規格）。另外，被移植掉的舊實作是一份**可執行的規格**——把舊邏輯拿原始值在腦中跑一遍，就能判定新行為是回歸修復還是新發明。

- **對外自動交付的觸發粒度，用對方看得懂的單位，不要用系統內部單位** — 把「何時推送/通知對方」掛在內部實作單位（檢體容器類型、內部分區、shard、佇列名）上，對方會體驗成「隨機的多次不完整交付」：內部單位對外不可理解也不可預測（同一種體液對應多個容器類型、目錄裡還有大小寫重複的條目），而且內部單位的「完成」常不含後算的衍生值（計算欄位、彙總分數），快照永遠缺一角。改掛在對方心智模型的單位（報告、成品、訂單）上：若上游已有「成品就緒」事件且 payload 同時帶「應有全集」與「已完成集」，完成度判斷就是純集合運算，衍生值也天然包含在內。實作省力法：最後一次「全部完成」交付讓既有的 final 路徑兜底，新粒度只需要一個前置條件（未完成集 ⊆ 豁免集 且 未完成集非空）加冪等 scope key——不用寫第二段交付邏輯。配套判斷：需求方已經逐項列出他要的分組並強調「我說得不能再清楚」時，照字面實作，不要替他再猜一層更聰明的分組；但 config 用集合而非布林，讓兩群是 N 群的特例，泛化不用改 schema。

- **Shared-quota bottleneck ≠ the segment you optimized** — 當一個 pipeline 撞共用資源限制（rate limit、訂閱 token 額度、連線池），把某段的單位成本砍 N× 後若整體吞吐只增 ~1.5×，瓶頸就不在那段——是另一個共用同資源的消耗者（常是同時在跑的互動 session 或別的 job）。先量「單位成本 vs 吞吐」的比例再下結論，別繼續優化錯的地方；要清 backlog 就讓該工作獨佔資源（無人值守／錯開時段）跑。

- **把紀錄轉手到新擁有者時，每個複製的欄位都要先問「它綁的是這件事，還是上一個擁有者」** — 「複製一份、只改該改的」看起來是最安全的重建方式（換負責人重新建立、照既有 peer 開新設定、從範本產生 stub），但真正的風險不是漏抄欄位，而是**照抄了一個綁定舊擁有者身分的欄位**。棘手處在於同一個欄位常同時承載兩種語意，取決於情境：一個「聯絡/會議資訊」欄位在視訊情境存的是**主持人的**個人會議室，在電話情境存的是**對方的**號碼——照抄對後者正確、對前者錯誤，於是 bug 只在一半的案例出現，回報起來像偶發。共同症狀有兩個，記住它們就能反向認出這個形態：**完全無聲**（沒有 error、沒有 log，值的型別與格式都合法）、而且**一律導向前一個擁有者**（人被帶進前一位主持人的會議室、資料被送到前一個 routing 目標）。硬規則：clone/mirror 的欄位清單要逐欄標記 owner-bound 或 entity-bound；owner-bound 一律**重新推導**而非複製，推導不出來時**清空並留 warn**，絕不保留舊值——保留舊值等於保證導向錯誤對象，清空只是缺資訊，後者可補、前者會造成實際傷害。分類查核很便宜：把該欄位在正式資料上按擁有者 group by，同一個值在單一擁有者身上重複幾十次 = owner-bound；每筆都不同 = entity-bound。另外，重新推導若需要呼叫外部 API，要放在交易**之外**——不要為了「一起原子」而讓一個 outbound HTTP call 卡在開啟的交易裡。
- **Caller 能自己修正的失敗要回 4xx，不要回 5xx** — 合法輸入推導出空結果是**拒絕**不是崩潰；回可被對方引用的 reason/code，且用對方送進來的詞彙回答，不要回內部 id。適用: 寫對外 API 的錯誤路徑、把上游錯誤往外轉、或看到 5xx 落在合法請求上時。


## 流程紀律

- **Agent 自創慣例進共享 repo 前，先問所有權層級** — 動工前確認 repo 是 personal 還是 company/team-owned：personal 由 owner 裁定即可；team-owned 時任何 agent 自創的工作慣例（wave doc、工作紀錄、檔案語言、命名規則）需整個團隊接受才能進 repo，否則放 instance repo 或既有 ticket 系統。單一協作者眼中「合理的慣例」（如英文 codebase 裡出現中文工作單）對團隊就是事故。適用: 建立新工作慣例、往產品 repo 放非產品文件、檔案語言與 repo 既有語言不一致時。子規則「code file 不進 CJK」enforced-by: `framework/hooks/validate-repo-language.sh`。子規則「wave doc 一律進中央 repo `agent-waves` 分 project path，不進 product repo」（Leo 指令 2026-08-16）——把最常見的自創慣例直接移出所有權判斷，product repo 永遠只留產品內容；2026-08-16 已把 industry-intel 的 9 份 wave doc 遷至 `agent-waves/industry-intel/`。
- **測試中發現的缺陷必須當場變 ticket，筆記不是追蹤** — E2E/測試/triage 過程中發現「不屬於當前工作範圍」的真實缺陷時，必須在同一個 session 內開正式 ticket（有 owner、有狀態、連結 parent），然後筆記引用 ticket id——絕不能反過來只在 memory/STM 寫一句 "proposed follow-up" 就結案。筆記沒有 owner、沒有 queue、對排程不可見；只存在筆記裡的已知缺陷功能上等同未知缺陷，而重新發現的成本往往由外部使用者/夥伴付。收尾檢查：關 ticket 前掃自己的工作紀錄，任何 "follow-up"/"wrinkle"/"proposed" 字樣而沒有對應 ticket id 的，都是還沒歸檔的缺陷。
- **Ticket 可以自己開，「這是 bug」的定性權在 owner** — 上一條的邊界：發現的問題要歸檔，但 issue type 不是中性欄位。標成 Bug 會進團隊缺陷統計、觸發必填的根因/分類流程、並隱含「現有行為是錯的」的裁決；很多從 code inspection 看到的「反模式」在 owner 眼中是刻意的權衡或待改進的設計，不是缺陷（owner 原話：「很多東西並不一定是這樣的」）。規則：agent 自行開的 ticket 用中性類型（task/story/improvement）並註明分類待 owner 確認，或開之前直接問；只有 owner 確認過才標 Bug。這與「別替其他團隊開 ticket」是同一族——歸檔義務是 agent 的，定性與分派的裁量權是人的。
- **Probe capability, not just errors** — 只對「有流量的錯誤」告警的監控，永遠抓不到零流量通道的損壞（域名失效、對端主機下線的低頻/休眠 integration）。對所有 enabled 的外送通道要週期性探測「能力」本身（DNS 解析、TCP 可達），否則通道壞掉的發現時間 = 下一筆真實流量失敗的時間，而那筆流量往往就是損失本身。
- **告警要掛在「最後一次成功產出」上，不是逐個 failure mode 補** — 誠實地把失敗寫進自己的 log ≠ 有人收到；而每次事故後只為剛壞的那一環加專屬告警，追不上 failure mode 的產生速度，下一個沒被涵蓋的環節照樣靜默數週。對每條 user-facing 通道記「最後一次成功送達的時間戳」，超過該通道的自然週期就告警——這個判準與失敗形態無關，天生涵蓋沒想到的那些。適用: 排程工作、推播/通知、批次交付。
- **行為變更沒有重讀過描述它的文件，就不算完成 — 而且漂移有兩個方向** — 「PR merge + ticket 關掉」不是收尾，「描述這個行為的文件被重新讀過且仍然成立」才是。兩個方向的漂移造成同一種傷害：有人照著關於系統的錯誤敘述行動。**方向一「文件承諾了程式沒做的」**：某 API 文件寫「staging 下單是 dry-run、不產生真實檢體」，實際上建真單真 accession id；同一份文件還把 500 列成正常且可重試的結果，等於教合作夥伴跟 bug 共存而不是回報它——外部測試者因此只能說「就是個 500」。**方向二「程式改了文件沒跟上」**：同一天內犯三次——(a) 我先寫下「部分品項無法履行時，訂單仍會以剩餘品項成立」，接著就實作了反轉此行為的 ticket，只因碰巧重讀該頁才發現；(b) cancel endpoint 改成「兩個識別碼都給要回 400」之後，文件仍在教對方「兩個都送時 placerId 勝出」——那正是被移除的行為，因為它會取消到**別張單**還回成功；(c) 新增了一個 error code 卻沒加進文件的 code 清單。後兩次我 PR body 與 ticket 描述都寫得很完整，卻從頭到尾沒打開過文件，是使用者問「文件要改嗎」才翻出來。三條配套：**(1) 宣告完成前 fetch 文件並搜尋剛改的行為**（含它所屬的回應／錯誤契約段落）——不能靠記憶判斷文件寫了什麼；**(2) 文件寫過舊行為時要明講「先前版本說 X，當時為真，現已不是」**，不要默默覆蓋，讀過舊版的人需要知道自己的理解變了；**(3) 新的 error code／reason／status 值，每一個都是一次文件編輯**。邊界：修正漂移不等於可以寫在程式前面——**仍然不寫尚未部署的行為**，那就是方向一重演。
- **Preserve evidence before restart** — hang 的 pod/process 在 restart/delete 前先 dump logs + describe，否則 root cause 隨 GC 永久消失。
- **Check live state before migration work** — 遷移/cutover 類工作開工前先讀 live config + 環境實況；ticket 系統的狀態 ≠ 環境實際狀態。
- **Worktree for parallel branches — 共用 clone 的並行 agent 同樣適用** — 多 branch 平行/stacked 工作用 git worktree，不要 in-place checkout（per-worktree 重建 deps）。**即使你只開一條 branch 也適用**：`git checkout` 改的是行程外的全域工作區狀態，共用同一個 clone 的其他 process 會把你的 HEAD 換走，接下來的 commit 靜默落到別的 branch（可能是受保護的 main）。共用 clone 上 commit/push 前一刻重驗 `git branch --show-current`。適用: 排程 agent 共用 repo、CI runner 共用工作區、任何多個自動化同時操作同一個 checkout。
- **輸出看起來錯但你的文字沒錯 → 去找顯示層，並用自己的 transcript 舉證** — 用戶反覆指出同一個「你寫錯了」而你的原始文字其實正確時，錯誤在**下游的顯示/轉換層**，那才是要修的地方；用「應該是渲染問題」結案等於把問題留給用戶重複踩。舉證方法：grep 自己的 session transcript（`~/.claude/projects/<slug>/*.jsonl`，解析 JSONL 並把 assistant 的 `text` block 與 `tool_use`/`tool_result` 分開統計），先證明自己到底有沒有輸出過那個字串，再往顯示層追。真實事故：用戶三次（相隔 11 天）指出 Jira 連結域名錯，前兩次我 grep repo/config 都沒找到就寫下「大概是 render-time 替換」；第三次去 grep transcript 才證明 assistant text 從未出現該字串，接著在**舊 session** 裡找到根因——一條 agent 自己寫的終端機 hyperlink 規則（`~/.wezterm-local.lua`，且當初刻意不進 git，所以任何 repo 搜尋必然是空的），把畫面上每個 ticket id 都連到錯誤網域。
- **grep 找不到只界定了搜尋範圍，不證明不存在** — 「我 grep 過，沒有」是無效結論，除非同時說出搜尋範圍。上面那個 case 前兩次搜的是 repo 檔案 + `~/.config` + `~/.zshrc` + `~/.wezterm.lua`，而目標檔案是 `~/.wezterm-local.lua`（刻意未追蹤）。報告時一律寫成「在 X、Y、Z 範圍內沒有」，並主動問「還有哪些地方可能承載這個行為」。
- **搜尋工具的 flag 用錯不會報錯，只會靜默降級成另一個搜尋** — 「我搜過了，沒有」的第二種失效（第一種見上一條的搜尋範圍）：命令根本沒在做你以為的事。兩個實際踩到的形態：(a) **需要參數的短 flag 與其他 flag 連寫**——`rg -r` 是 `--replace`，所以 `rg -rn pat` 等於 replacement=`n`，`rg -ril pat` 等於 replacement=`il`，而 `-i`/`-l`/`-n` **全部沒生效**；輸出裡每個匹配都被替換成那個字面值，看起來像亂碼，而失去 `-i` 讓搜尋變成大小寫敏感、直接漏掉 `Foo` 這種命名。(b) **借用別的工具的選項名再吞掉錯誤**——把 grep 的 `--include` 用在 rg 上，配合 `2>/dev/null`，就把「工具用錯」偽裝成乾淨的「0 hits」。三條配套規則：**flag 分開寫、不與帶值的 flag 相鄰**；**確認 0 命中之前先把命令重跑一次且不要 redirect stderr**；**輸出看起來被亂改時，先懷疑自己的命令，再懷疑環境**——上一條 lesson 的正解是顯示層，但前一次的結論不是這一次的先驗，我就是照著那個先驗把自己的 flag bug 誤診成終端機問題。
- **關鍵字命中不等於覆蓋 —— 用「無法從主題推導出來」的字串驗證** — 「我搜過了，有」的失效（前兩條是「沒有」的兩種失效）：判斷某件事是否已被記錄/實作過時，搜主題詞會被談論同一主題的無關段落命中，於是把「有提到」誤判成「已覆蓋」。改搜只有真內容才會出現的字串——API 名、欄位名、識別碼、錯誤訊息原文；主題詞猜得到，這些猜不到。適用: 去重、蒸餾記憶、盤點「這條規則是不是已經寫過了」、判斷某功能是否已存在時。

- **絕不從使用者的 email 域名推導組織的 URL/識別碼** — 登入信箱網域 ≠ 組織的服務網域（`hung.l@zymebalanz.com` vs Jira 站 `vibrantamerica.atlassian.net`）。不知道正確值就去查真實來源（既有連結、API、config）或直接問；一次憑空猜測換來三次打擾、一個錯誤的補救方案，以及 22 天畫面上每個 ticket id 都指向不存在的站。
- **repo 裡的部署設定不是 runtime 真相 — 而且兩個方向都會騙你** — 版控裡的 manifest/ConfigMap 常年與實際部署 diverge（真正生效的是 cluster 裡的物件、外部 secret manager、或某台機器上的未追蹤檔案）。兩種相反的誤讀都踩過：(a) **設定裡沒有 → 誤判功能沒在運作**：某個環境變數在 repo 的所有 manifest 都找不到，我因此推論它從未被注入、對應欄位長年為空，準備開 bug ticket 並為了消警告把該欄位的寫入從 code 拿掉；實際查 prod 是 5370/5372 筆都有正確值——那個變數由實際部署注入，repo 的 manifest 目錄根本不是部署來源。(b) **設定裡有 → 誤判功能存在**：新服務留著上一代的設定佔位符（DSN、webhook URL），但整個 SDK/實作都沒遷移過來，所以那些 key 是「曾經有這個能力」的化石，不是「現在有」。硬規則：對「這個東西有沒有在運作」的判斷，一律去 runtime 取一筆真實資料（prod 一個 `COUNT` 就夠）再下結論；**絕不讓 linter/pre-commit 警告驅動 code 決策**——我當時為了讓檢查通過，把該欄位的寫入直接從新路徑移除，那是真的行為退化（該路徑不再記錄是哪個實例處理的），只為消一個誤報。要嘛修工具，要嘛在 commit 說明為何豁免，不要改產品行為去迎合工具。附帶：這類 guard 若只檢查 ConfigMap，就會對「放在 secret 的變數」和「靠 downward API 注入的變數」永久誤報，該修的是 guard。

- **Debug 從 header/證據本身下手** — 例：debug CORS 永遠 grep `access-control-allow-origin` 本身；framework 可能回 204 + 其他 header 造成假象。
- **宣稱「更乾淨」前先驗隱藏相依** — 追求更好的設計沒問題，但改之前確認沒有隱藏耦合（env、cache、singleton）。
