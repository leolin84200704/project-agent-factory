# Proposal: 重新設計一條規則之前，先交出「現況 baseline」——放在給人看的訊息裡

## 候選教訓（standalone 版本，無 domain 名詞）

> 任何「改掉現行比對／路由／解析規則」的討論、盤點或資料收斂，交付物 #1 是一頁
> **現況 baseline**，先於任何提案與變更：
> 1. 現行規則的**輸入與分支**，讀真 code（含存在但可能沒人走的路徑）；
> 2. **每條路徑今天實際誰在走**，用原始輸入（raw payload）驗證——系統解析後存下的
>    欄位不是「發送端送了什麼」的證據；
> 3. tie-break 規則，以及哪些欄位是「選中後帶出的輸出」、哪些是「比對條件」。
>
> baseline 必須出現在**給決策者的訊息裡**，不能只埋在報告檔的註記——知道不等於講了，
> 決策者拿不到共同模型，就會在不完整的模型上下指令，而 agent 照單全收等於替錯誤順序背書。

## 為什麼是 discipline 而非 behavior

規定的是工作順序（提案之前先交現況）與溝通位置（訊息本文、非附件），不描述任何系統
如何運作。可檢查化：規則變更類任務的第一份交付物裡，若沒有「現行行為」段落即違規。

## 證據（單一 domain，這是它卡住的原因）

一次訂單路由規則重設計：agent 從第一天就知道現行比對邏輯（自己的工作紀錄裡寫著），
但第一份盤點交付完全圍繞「新 key」視角，現況只以一句括號註記埋在報告檔開頭。後果：
1. 決策者花了約 7 個 turn、跨兩天，用問答逆向工程現行系統（「來一筆訂單我們怎麼知道
   下到哪？」「除了 A 欄位還會看 B 欄位嗎？」「以這個例子從頭講一次流程」）。
2. 決策者在不完整（單一識別碼中心）的模型上下了 prod 資料收斂指令，agent 未 push back
   就執行——事後才發現有一條低頻但真實的路徑用的是另一種識別碼。
3. prod 資料變更先於「各發送端實際送什麼欄位」的普查完成；普查跑完後顯示原設計假設
   （practice 欄位可用）只覆蓋 24% 的訂單。
完整模型直到開工約 28 小時後、被決策者強制要求「從頭到尾講一次」才第一次完整出現。

## 若要升格成正典，還缺什麼

第二個**不同** domain 的案例。形態應該是：一次規則/介面/排程的重設計討論，因為現況
基準沒被放上桌（或只存在 agent 腦中／附件裡），導致決策者在錯誤模型上做出指令、
或方案討論反覆而無效。
