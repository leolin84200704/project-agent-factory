# Proposal — 跑不起來的自動化工作必須主動告警，寫進 log 不算

> Status: unreviewed inbox item (LIS dream 2026-08-01)
> Target if accepted: `framework/ENGINEERING-LESSONS.md` § 流程紀律

## 草擬條文

**跑不起來的排程工作必須主動告警；「BLOCKED」寫在自己的輸出裡不構成通知。** 排程工作有三種結局：
成功、發現問題、**根本沒跑成**。第三種最危險，因為它的外顯形式和「跑了，沒發現問題」完全一樣 ——
兩者都是「今天沒有人來找我」。工作本身很老實地把 `BLOCKED / 前置條件不可達 / 重試三次全失敗`
寫進自己的 log 或輸出檔，然後沒有任何人讀那個檔案，於是它連續失效好幾天都無人察覺。

紀律：(a) 前置條件不可達時，退出碼與通知管道要跟「發現問題」同級，不能只留一行 log；
(b) **readiness 探測要探真正要用的那個相依**，不是探一個比較容易通過的代理指標；
(c) 監看自動化的健康要看「最近一次成功產出的時間戳」，不是看它有沒有噴錯 —— 沒有輸出跟輸出「一切正常」
在儀表板上長得一樣，但意義相反；(d) 一個宣告自己 BLOCKED 的工作，**在它被修好之前，那段時間是無資料，
不是無問題**，任何「這幾天都很乾淨」的結論都不能建立在它的沉默上。

## 為什麼可能是通用的（跨領域證據）

1. **實驗室資料 triage 工作（employer domain，有 prod 後果）**：每日排程檢查失敗紀錄的工作，因為前置的
   網路通道沒連上，連續 3 天把「BLOCKED — 資料庫不可達；這不代表沒有失敗紀錄」寫進當天的輸出檔就結束。
   沒有任何告警。結果一筆真實的失敗案件在無人知情下擱置約 2 天，直到另一個流程從別的路徑（服務自己的
   容器內）繞過去查才發現 —— 而那條替代路徑一直都可用，工作只是沒被教會要試。
2. **記憶整併排程（個人 agent 基礎設施）**：同一週某晚 3 次嘗試全部以 DNS 解析失敗告終，log 寫著
   `FAILED after 3 attempts`。有趣的是它的 readiness 探測在失敗前 1 分鐘還回報「網路就緒」——
   它探的是一個比實際要用的 API 端點寬鬆的條件。整晚沒有產出、沒有告警，隔天也沒人發現，
   是後來的執行去翻 log 才知道少了一天。
3. **每日摘要工作（個人 agent 基礎設施）**：最後一次產出停在某日之後就沒再出現，同樣無聲。
   發現方式同上 —— 靠人偶然去 `ls` 那個目錄。

三個案例的共同結構：工作很誠實地記錄了自己的失敗，而**誠實的記錄不等於送達**。

## 與現有條文的關係

- 與 § 流程紀律「Probe capability, not just errors」同源但不同面：那條講**對外通道**要主動探測能力，
  這條講**自己的排程工作**失效時要主動告警，並且 readiness 探測本身會騙人。
- 與 § 驗證紀律「安靜的觀測窗不是故障證據」是同一枚硬幣的反面：那條說「沒產出不代表壞了」，
  這條說「沒產出也不代表好了」——兩者共同的要求是**去量輸入端／去確認工作真的執行過**。

## 未達標的地方（為什麼進 inbox 而不是開 PR）

跨領域證據偏弱：3 個案例裡有 2 個都是「我自己的排程工作」，嚴格算起來接近同一個 domain。
第 1 個案例有真實 prod 後果、屬於另一個系統，但單獨一個案例撐不起「跨領域」。
若日後在第三方 CI／別的雇主系統上再踩到同一形狀，再升成 PR。
