# Proposal — fallback 若是在「猜」，就必須 fail loud；交付成功不等於內容正確

> Unreviewed inbox item (2026-08-06). Single-domain evidence so far → not a PR.
> Promote only if a second, different-domain case shows up.

## Lesson (de-identified, standalone form)

兩條互相咬合的規則：

**(1) 降級路徑產出的是「合法但可能錯」的內容時，它不是降級，是靜默造假。**
一個主要資料來源（唯一知道「使用者到底要什麼」的那個 API/表）呼叫失敗後，若程式 catch 掉、
改用一個「用手上現有資料推測」的次要演算法，而該演算法的輸出**在格式上完全合法**、
下游會照常接收處理 —— 那麼失敗就變成了一份看不出錯的錯誤產物。此時正確設計是
**throw、讓上層 retry**（transient 失敗 retry 就會對；靜默猜測永遠不會對），
而不是回一個看起來像成功的結果。

要留退路時，把猜測路徑放在**明確的 env 開關後面且預設關閉**：語意從「悄悄降級」
變成「有人明知代價地打開它」，而且不必 deploy 就能恢復。

判斷法：問「這條 fallback 的輸出，錯了會被誰擋下來？」如果答案是「沒有人，格式是合法的」，
它就必須 fail loud。特別危險的形態是 **first-match / 取第一個相符者** 這類演算法：
只要候選集合裡存在一個「超集」項目，它幾乎永遠會贏，於是所有輸出都被貼上同一個錯標籤。

**(2) 「交付成功」不能證明「內容正確」，兩者要用不同的證據驗。**
交付面的紀錄（狀態欄位、傳輸時間、檔案落地、對方已取走）全綠，只證明搬運正確。
內容是否正確，必須把**實際送出的內容**跟**定義該內容的權威來源**對撞（送出的分類標籤
vs. 上游訂單系統說使用者實際訂了什麼）。只看交付狀態的 triage 會直接錯過整整一類 bug。

附帶一條便宜的取證技巧：要證明「當時走的是哪條路徑」而現場 log 已過期時，
**用今天的資料離線重放舊演算法**，看能不能精確重現當時的產物分佈。能重現就是路徑證明，
不需要當時的 pod log。

## Evidence

- **LIS / EMR result HL7 OBR 標籤（2026-08-06, VP-17631）**：診所抱怨收到的檢驗報告列出三個
  他們沒訂的套組，點進去的項目跟套組名稱不符，懷疑是別人的病人。DB 端一片綠 —— 只有一筆投遞、
  狀態 TRANSMITTED、無 error、檔案確實上傳且對方已取走。真因在**內容**：分組服務把
  「查詢實際訂購內容」的 API 的任何失敗都 catch 掉，改用 legacy first-match 演算法
  （每個項目指派給第一個包含它的套組），而該對照表的**第一個 key 恰好是一個 117 項的超集套組**，
  於是幾乎所有常規項目都被蓋成那個套組名。用今天的對照表離線重放該演算法，
  精確重現了當時檔案的項目分佈（74/1/5/2），確認走的是 fallback。同一演算法在 8 個月間
  造成 12 筆誤標投遞（跨 4 個 vendor）；當天其他投遞都正確，且同一支樣本今天 API 正常
  → 是 transient 失敗，retry 就會對。修法：transport 失敗與「回 200 但什麼都沒歸屬」都改 throw、
  legacy 路徑收進預設關閉的 env 開關、未被歸屬的資料改為大聲 warn（原本靜默消失 11 個項目）。

## Why it might be universal

(1) 講的是錯誤處理的設計判準（降級輸出的可稽核性），不依賴任何特定系統；
(2) 講的是驗證證據的分層（搬運 vs 內容），同樣與領域無關。兩者都可能只是
既有 fail-loud 家族規則的一個新面向 —— 現有規則講的是「失敗要留痕跡」，
這裡多的是「**失敗留了痕跡也不夠，因為產物本身看起來是合法的**」。
需要第二個不同領域的案例才升級成 PR。
