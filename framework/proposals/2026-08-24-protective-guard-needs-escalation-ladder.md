# Proposal — 拒絕執行的防護閘需要升級梯，不能無限期靜默停機

> Status: unreviewed inbox item (LIS dream 2026-08-24)
> Target if accepted: `framework/ENGINEERING-LESSONS.md` § 流程紀律
> Sibling: `2026-08-01-a-job-that-cannot-run-must-alert.md`（已升級成 output-liveness
> 條文）。那條講**監看端**要看最近一次成功產出；本條講**閘本身**的設計義務 ——
> 兩者互補：liveness 監控是外部保險，升級梯是閘不把自己變成事故的內建義務。

## 草擬條文

**一個因前置條件不滿足而拒絕執行的防護閘，必須內建升級梯；「每次都拒絕」不是安全行為，
是把單一小故障放大成無上限停機。** 防護閘拒絕執行通常是對的（髒狀態下硬跑會造成
更糟的損壞——同系統確實發生過）。錯的是拒絕之後**什麼都不做**：閘每晚同樣地拒絕、
同樣地把原因寫進沒人讀的 log，被守護的功能無限期停擺，而觸發條件可能只是一次
被遺忘的 commit。設計紀律：第 1 次拒絕可以只留紀錄；**連續第 2 次拒絕起必須升級**
——大聲通知負責人，或降級成不觸碰髒狀態的 read-only / 部分執行模式，讓「停機」
不可能超過一個週期無人知情。判斷一個閘要不要升級梯的測試：**觸發它的最小人為失誤
是什麼？該失誤被發現前，閘會拒絕幾次？** 若答案是「無上限」，這個閘缺升級梯。

## 案例（為什麼還不到 PR 門檻）

1. **記憶整併 pipeline 的 dirty-tree 閘（agent 基礎設施）**：nightly 整併在 tracked
   記憶檔有未 commit 修改時拒絕啟動（正確——前一週 autostash 硬跑真的疊壞過一晚的
   產出）。一次被遺忘的 commit 讓它連續 3 晚拒絕，整個蒸餾層停擺，唯一症狀是索引檔
   裡一個沒人重讀的日期。第 4 天靠 session 啟動時的 staleness 檢查才發現——備援有效，
   但慢了三天。期間有一張 ticket 的關閉永久滑出稽核窗（後靠改窗口定義補救）。
2. （同 domain 反面教材）同一 pipeline 兩週前的版本沒有這個閘、用 autostash 硬跑，
   把部分重生內容疊在已 commit 的蒸餾上，一天後才被發現。**閘該存在**；本條只修
   「拒絕之後」的行為。

跨領域證據不足：兩個案例都是同一條 pipeline（一正一反）。CI 的 required-check、
部署系統的 frozen-window 等第三方系統理論上同形，但我還沒實際踩到。踩到第二個
domain 的實例時升級成 PR。

## 與現有條文的關係

- output-liveness（sibling 升級後的條文）：監看者看「最近一次成功產出」可以抓到本案
  ——但它假設有人裝了監看。本條把義務放進閘自身，兩條在不同層各自成立。
- 「安靜的觀測窗不是故障證據」：同結構——沉默不攜帶資訊；本條讓閘的沉默最多存活一個週期。
