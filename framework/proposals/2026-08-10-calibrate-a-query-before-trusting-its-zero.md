# Proposal — 把「零筆」當證據之前，先用一個已知正例校準這個查詢

> Unreviewed inbox item (2026-08-10). 證據跨了三個不同領域，但與既有的
> 「安靜的觀測窗不是故障證據 — 要量輸入端」高度相鄰，可能只是同一條的另一面。
> 由 Leo 判斷是併入既有條目、獨立成條、還是不收。

## Lesson (de-identified, standalone form)

**一個回傳零筆的查詢，只有在你確認過「它查得到東西」之後才是證據。**

「沒有錯誤」「沒有輸出」「檔案不在」這類結論幾乎都建立在某個查詢的空結果上，
而空結果有兩種完全不同的成因，長得一模一樣：

1. **真的沒有** —— 那件事沒發生。
2. **儀器對準了錯的欄位** —— 事情發生了，但你的過濾條件、時間窗、權限或資料路徑
   讓它永遠不可能出現在結果裡。

第二種在事後看都很蠢，在當下都很合理，因為查詢語法沒有錯、也不會報錯——它只是回零。
而「回零」正是你預期看到的形狀，所以不會有任何東西提醒你重新檢查。

**做法：在下「沒發生」這個結論之前，先跑一次你已知會有結果的版本。**
拿掉最可疑的那個過濾條件、把時間窗往回拉到一件你確定發生過的事、
或直接查一筆你親眼見過的紀錄。如果放寬之後**還是零**，那零就是假的，問題在儀器。
這通常是三十秒的事，換掉的是一個方向完全相反的結論。

推論兩條：
- **「我查了 N 小時都沒有」要先問這 N 小時從哪裡開始。** 保存期限、輪替、重建、
  權限邊界都會讓觀測窗的實際起點遠晚於你以為的起點。
- **報告空結果時，要一起報告校準結果。** 「查無」單獨出現沒有資訊量；
  「查無，且同一查詢在已知正例上會回 N 筆」才是證據。

## Evidence

- **可觀測性平台的 severity 欄位（2026-08-10，某後端服務的 P1 事故）**：追一個「下載報告失敗」的
  P1，三個獨立來源都說沒有錯誤 —— pod log 48 小時 3,866 筆請求全部 200、ingress 零 4xx/5xx、
  監控平台 `status:error` 零筆。實際上那週有 236 次 500，事故當天尖峰失敗率約 10%。
  三個零各有各的假象：(a) pod log 只涵蓋 pod 壽命，而全 cluster 的節點在事故隔天維護時換過，
  所有 pod 只有 42 小時大 —— 「查了 48 小時」的窗其實是從事故**之後**才開始的；
  (b) 該服務的 logger 沒有做 severity remap，error 級別全部落成 `status:info`，
  於是 `status:error` 對這個服務**永遠**回零，正確查法是依錯誤型別或 HTTP 狀態碼欄位；
  (c) 被瀏覽器 CORS 擋掉的請求，server 端只會留下一筆乾淨的 preflight 204。
- **作業系統排程器的 stdout（2026-08 前後，連續三晚誤判）**：某排程工作的 stdout 檔案永遠是 0 bytes，
  於是「沒有輸出」被讀成「工作沒跑」，連續三晚判定該工作已死。實際上工作每晚都正常執行，
  只是它把自己的紀錄寫在別的地方 —— 排程器捕捉到的 stdout 本來就永遠是空的。
  這裡的校準只要問一句「這個檔案曾經有過內容嗎？」就會發現它從第一天起就是 0 bytes。
- **作業系統的權限保護目錄（macOS TCC）**：對受保護目錄下 `ls` / `find` / 索引搜尋全部失敗或空白，
  被讀成「檔案不存在」。實際上檔案在，權限擋的是**列目錄**而不是**直接存取**；
  對完整路徑直接 stat 立刻就能拿到。「列不出來」與「不存在」是兩件事，而工具的輸出一樣。

三個案例分屬三個不同領域（可觀測性查詢 / 排程器 / 檔案系統權限），
共同形狀是：**工具沒有報錯，只是它結構上不可能給出正例**。

## Why it might be universal

它規定的是一種工作方式（下否定結論前先校準工具），不描述任何特定系統的行為，
文字裡沒有任何領域名詞，把案例拿掉後規則本身依然完整。

與既有條目的關係：`ENGINEERING-LESSONS.md` 的「安靜的觀測窗不是故障證據 — 要量輸入端」
處理的是**輸入端真的為空**（系統健康，只是沒東西可做）。這一條處理的是**輸入端不為空，
但儀器看不到它**。兩者的症狀完全相同（一個零），但排除方法不同：
前者去量上游產生了多少，後者去校準查詢本身。
若要收，可能適合作為該條目底下的第二種零，而不是另立新條。
