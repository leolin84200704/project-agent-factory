## 前言：這本書在講什麼

想像你雇了一位非常聰明、但每天早上醒來就忘光昨天所有事情的工程師。他讀過全世界的書，
手腳很快，但你昨天教他的公司規矩、他昨天踩過的雷，今天全部歸零。

這就是大型語言模型（LLM）當工程助手的原始狀態。這本書記錄的是一個真實的工程專案：
如何給這位「金魚腦天才」裝上記憶、讓他晚上「睡覺做夢」整理白天學到的東西、讓他踩過
的坑變成永久的紀律、並且——最難的部分——**用數據證明他真的一天比一天好用**，而不是
憑感覺。

書分五部：
- **第一部（第 1–4 章）**：零基礎概念。LLM、agent、context window、為什麼檔案是最好的記憶。
- **第二部（第 5–9 章）**：這座「工廠」的解剖。雙 repo、記憶分層、夢境管線、教訓的階梯。
- **第三部（第 10–13 章）**：坑的圖鑑。這套系統實際死過的每一種方式，與修法。
- **第四部（第 14–17 章）**：量測。2026-08-15 的升級：怎麼科學地回答「它有進步嗎」。
- **第五部（第 18–19 章）**：前後對照、界限與開放問題。

# 第一部：從零開始

## 第 1 章　LLM：一台會接話的機器

大型語言模型（Large Language Model, LLM）本質上做一件事：**給定一段文字，預測下一個
字**。它讀過網際網路規模的文字，所以「預測下一個字」的能力強到可以寫程式、講解法律、
翻譯詩。ChatGPT、Claude、Gemini 都是這類模型。

要記住兩個對後面所有章節都關鍵的性質：

1. **它是無狀態的（stateless）**。模型本身不會因為跟你講過話而改變。你們的對話結束，
   它「腦中」什麼都沒留下。所謂「它記得上一句」，只是因為整段對話被重新塞給它看一次。
2. **它是機率性的（nondeterministic）**。同一個問題問兩次，答案可能不同。這個性質在
   第 16 章會回來咬我們一口——當你以為抓到 bug 的時候，先確定你不是抓到了機率。

**資料來源**：Vaswani et al., *Attention Is All You Need*（arXiv:1706.03762, 2017）——
現代 LLM 的 Transformer 架構起點；Brown et al., *Language Models are Few-Shot Learners*
（arXiv:2005.14165, 2020）——「大模型讀 context 就能學會做事」的奠基實證。

## 第 2 章　Agent：給模型手和腳

單純的 LLM 只能「說」。**Agent（代理人）= LLM + 工具 + 迴圈**：讓模型可以說「我要執行
`ls` 指令」，系統真的去執行，把結果貼回給模型看，模型再決定下一步。重複這個
「思考 → 行動 → 觀察」的迴圈，模型就能完成多步驟的真實工作：讀程式碼、改檔案、跑測試、
開 pull request。

這個迴圈模式在學術上的代表作是 ReAct（Reason + Act）。工程上的實例就是本書的舞台
Claude Code：一個在終端機裡運行的 coding agent，能讀寫檔案、執行指令、操作 git。

Agent 與聊天機器人的本質差異：**agent 的錯誤會落地**。聊天說錯話無妨；agent 下錯一條
`DELETE` 是真的刪資料。所以本書後半的大量篇幅在講欄杆（hooks）、紀律（lessons）、
與驗證（evals）。

**資料來源**：Yao et al., *ReAct: Synergizing Reasoning and Acting in Language Models*
（arXiv:2210.03629, 2022）；Anthropic, *Building effective agents*（anthropic.com 工程部落格, 2024-12）。

## 第 3 章　金魚腦問題：context window 與遺忘

模型每次「思考」時能看到的全部文字，叫 **context window（上下文窗）**。它像一塊白板：
你的指示、對話歷史、它讀過的檔案，全都要寫在這塊白板上模型才「知道」。白板有大小上限
（數十萬 token 級），而且有三個殘酷的性質：

1. **session 結束即擦白板**。明天的 agent 不記得今天的任何事。
2. **白板越滿，讀得越差**。實驗顯示即使遠未到上限，塞進越多內容，模型對其中每一條的
   遵守度與檢索力就越低——這叫 context rot（上下文腐蝕）。一項 500 條指令的壓力測試
   顯示：前沿模型到約 150 條指令後開始系統性掉隊，而且是「每加一條、所有舊條目都
   一起變差」的均勻稅。
3. **遵守度隨 session 變長而衰減**。對 Claude Code 的 1,650 場實測顯示，寫在指示檔裡的
   規則，每多產出一個函式，被遵守的機率就再降一點。

這三個性質決定了本書所有的架構選擇：記憶必須放在白板**之外**、按需取用、而且常駐白板
的內容必須極度節制。

**資料來源**：Chroma Research, *Context Rot*（trychroma.com/research, 2025-07）；
Distyl AI, *IFScale* 指令遵守壓力測試（arXiv:2507.11538, 2025）；McMillan,
Claude Code 指令遵守因子實驗, 1,650 sessions（arXiv:2605.10039, 2026）。

## 第 4 章　最笨也最強的記憶：純文字檔案

「給 agent 記憶」聽起來應該用什麼向量資料庫、知識圖譜的高科技。2025–2026 年的實證給了
一個反直覺的答案：**把記憶寫成 Markdown 檔案、用 grep 搜尋**，是被證明極強的 baseline。

三個證據：
- 一項針對記憶產品評測亂象的獨立分析發現：在被兩家商用記憶產品（Mem0、Zep）拿來互打
  行銷戰的基準測試上，一個「把對話歷史存進檔案 + grep」的簡單 agent 拿到 74 分，
  **勝過兩家的爭議配置**。
- 學術先驅 MemGPT 的團隊（Letta）在 2026 年 3 月把整個產品線轉向 **git 版本化的檔案
  記憶（MemFS）**，棄置了自家原本的伺服器端記憶工具。
- 蘇黎世聯邦理工（ETH Zurich）對真實 repo 的對照實驗顯示：專案說明檔（AGENTS.md 類）
  平均**不提升**任務成功率、還增加 20%+ 成本——**唯一有效的內容是「模型自己推不出來的
  明確指令」**。這條發現定義了什麼值得寫進記憶：不是文件，是「不可推斷的事實與規則」。

檔案記憶的額外紅利對工程師特別重要：git 可版本化、可 diff、可 code review、換一家模型
供應商也帶得走。本書的主角系統從第一天就建立在這個地基上。

**資料來源**：*Benchmark Theatre* 記憶評測分析（bloo-mind essays, 2026-05）；Letta,
*Our Next Phase*（letta.com/blog, 2026-03）；Packer et al., *MemGPT*
（arXiv:2310.08560, 2023）；ETH Zurich, *Evaluating AGENTS.md*（arXiv:2602.11988, 2026）。

# 第二部：一座工廠的解剖

## 第 5 章　雙 repo：大腦與身體分離

project-agent-factory 的第一個架構決定：**每個工作領域配一對 repo**。

| | 名稱範例 | 裝什麼 |
|---|---|---|
| **大腦（instance repo）** | `industry-intel-code-agent/` | agent 的角色設定（CLAUDE.md）、記憶（STM/LTM/journal）、自我精進腳本（dream、eval） |
| **身體（工作 repo）** | `industry-intel/` | 產品程式碼本身 |

為什麼分開？三個理由：
1. **記憶的 git 歷史不污染產品的 git 歷史**。agent 每天寫記憶，若混在產品 repo 會把
   commit log 灌成垃圾場。
2. **可攜**。換工作、換專案，大腦的「方法論」部分可以複製繁殖（見第 9 章的 factory）。
3. **權限邊界**。產品 repo 可以有「push 到 main 會觸發部署」這種地雷；大腦 repo 隨便 commit。

工作 repo 裡只放三樣輕的東西：一行指回大腦的指標（`@../xxx-code-agent/CLAUDE.md`）、
關閉原生自動記憶的設定、指向共用安全欄杆（hooks）的絕對路徑。第 13 章會講漏掉那行
指標的真實代價。

而在所有大腦之上有一個**祖父層：factory repo**（project-agent-factory 本身），放跨工作
通用的東西：個人工作習慣（AGENTS.md）、通用工作流程（work loop）、記憶協議
（RETRIEVAL.md）、以及全體 agent 共享的工程教訓（ENGINEERING-LESSONS.md）。
每個 agent 稱為一個 instance，有代號：`lis`（工作機）、`iic`、`jac`（個人機）。

## 第 6 章　記憶分層：像人腦一樣有短期與長期

大腦 repo 裡的記憶不是一坨檔案，是有分層的，靈感直接借自認知科學：

| 層 | 對應人腦 | 內容 | 誰能寫 |
|---|---|---|---|
| L1 | 性格與本能 | CLAUDE.md：角色、規則、常駐紀律 | 人（Leo） |
| L2 | 「我知道我知道什麼」 | `_index.md`：帶分數的目錄表 | 自動腳本 |
| L3a | 情節記憶（episodic） | journal/：每場工作的敘事——探索過什麼、排除過什麼、為何這樣決定 | agent，session 結束時 |
| L3b | 語意記憶（semantic） | STM（每張任務一檔）與 LTM（蒸餾過的領域知識） | STM 隨工作寫；**LTM 只有 dream 能寫** |
| L4 | 現實世界 | ticket 系統、GitHub、資料庫、正式環境 | 沒人——只能讀 |

配套一份**檢索協議（RETRIEVAL.md）**回答「什麼問題查到哪一層就停」。兩條最重要的規則：

- **記憶指涉世界，不包含世界**：回答「現在狀態如何」之前，必須對 L4（真實系統）查證。
  記憶說「已部署」不算數，GitHub 上 PR 真的 merged 才算數。
- **Session 開始只讀目錄（L2），不預載內文**：白板空間珍貴（第 3 章），要用才翻。

每份記憶檔有 frontmatter 元資料（分數、時間、標籤），分數按「新近度 × 被引用次數 ×
緊急度」隨時間衰減——冷掉的記憶自動沉底、歸檔、最終遺忘。遺忘是功能不是 bug：不遺忘
的記憶庫終將壓垮檢索。

**資料來源**：分層與外部記憶概念——Packer et al., *MemGPT*（arXiv:2310.08560）；
原子筆記與自動連結——Xu et al., *A-MEM: Agentic Memory*（arXiv:2502.12110, NeurIPS 2025）；
遺忘曲線工程化——Ebbinghaus 記憶衰減的現代應用（Mem0 production decay 設計, 2025-26）。

## 第 7 章　夜間的夢：dream pipeline

人腦在睡眠中把白天的經驗固化成長期記憶。這套系統照抄了這個機制：每晚固定時間，
排程器（macOS launchd）喚醒一個無人值守的 agent 跑「**dream**」，五個階段：

1. **對現實對帳（reconcile）**：拿 STM 記錄的任務狀態去對 L4——ticket 關了沒、PR merged
   沒、資料檔長大了沒——把過時的狀態翻正。
2. **增量掃描**：只讀上次 dream 之後動過的檔案（全量掃描曾在 50+ 檔案時壓垮過管線）。
3. **蒸餾（distill）**：把 journal 裡的敘事萃取成 LTM 的規則與知識；合併重複、解決矛盾
   （信新不信舊，但留下取捨記錄）；跨任務找模式。
4. **評分與重建索引**：跑衰減公式、重建 L2 目錄。
5. **寫 dream log**：這一晚做了什麼，人類可稽核。

兩條鐵律：
- **LTM 只有 dream 能寫**。工作中的 agent 只寫 journal。曾經允許雙寫，結果是同一條知識
  兩份措辭互相矛盾——單一寫入路徑是從血淚換來的。
- **Delta 更新，絕不整檔重寫**。研究實測過一個 18,282 token 的知識庫被模型「重新整理」
  一次後崩塌成 122 token、效果掉到比沒有記憶還差——這叫 context collapse。dream 只允許
  逐條增改。

「睡眠時間計算」在學術上有直接支持：離線整理記憶的 agent，可以用 5 倍少的即時計算達到
同等準確率，睡眠計算投入越多、白天表現越好。

**資料來源**：Letta, *Sleep-time Compute*（arXiv:2504.13171, 2025）；context collapse 與
delta 更新——Stanford/SambaNova, *ACE: Agentic Context Engineering*（arXiv:2510.04618,
ICLR 2026）；Anthropic 原生 auto memory 文件（code.claude.com/docs/memory, 2026）。

## 第 8 章　教訓的階梯：從一次踩雷到全體免疫

這套系統最有野心的機制：**一個 agent 踩的坑，變成所有 agent 的紀律**。流程像疫苗研發：

1. 工作中踩雷 → 記進該任務的 STM `Failures` 區段（含完整錯誤與當時的錯誤假設）。
2. 任務收尾做 **retrospective（復盤）**：預測 vs 實際、失敗可否預防、1–5 分自評信心度。
3. session 結束寫 journal。
4. 夜裡 dream 蒸餾 journal；若判斷某條教訓「換一家公司也成立」（job-agnostic），
   就向 factory repo 開一個 **lesson PR**：教訓本文去識別化（不含公司名、客戶名、
   ticket 編號），佐證細節寫在 PR 說明裡。
5. **人（Leo）審核後才 merge**。審核標準：至少兩個案例或一次事故佐證（單一案例不收——
   防過度概括）、與現有條目不矛盾、去識別化乾淨。
6. merge 後，所有 instance 下次 pull 就繼承這條紀律。

2026-08-15 為止，這座階梯已經運出數十條紀律，例如「批次資料庫寫入後驗證 100% 的列、
絕不抽查」「清理用的 DELETE 其 WHERE 必須綁定當次操作範圍」——每一條背後都是一次真實事故。

格式上的講究有實證支持：教訓以「**標題 + 一句可執行原則**」的 insight 形式儲存，效果
勝過存工作流程、更勝過存原始對話記錄（兩項獨立研究一致）；每條限 ~50 字（過長的教訓
庫會撞第 3 章的指令天花板）；而且**刪除與修訂跟新增同等常規**——只加不減的教訓庫終將
自我中毒。

**資料來源**：insight 形式優於 workflow/trajectory——Google Cloud AI, *ReasoningBank*
（arXiv:2509.25140, ICLR 2026）與 KAIST/NYU, *Memory Transfer Learning*（arXiv:2604.14004,
2026）；跨任務教訓蒸餾的先驅——Zhao et al., *ExpeL*（arXiv:2308.10144, AAAI 2024）；
復盤機制的祖先——Shinn et al., *Reflexion*（arXiv:2303.11366, NeurIPS 2023）；
字數上限——Tencent, *Training-Free GRPO*（arXiv:2510.08191, 2025）；多 agent 共享記憶的
收件匣→審核→正典模式——Microsoft Squad 工程部落格（2026）。

## 第 9 章　欄杆與繁殖：hooks 和 BOOTSTRAP

**Hooks（欄杆）**：agent 的每次工具呼叫前，系統可以先跑一段確定性的腳本。這套系統用它
擋不可逆操作：`git push --force`、`git reset --hard`、對正式資料庫的寫入指令。關鍵字是
**確定性**——寫在指示裡的「請不要 force push」會隨 session 變長而被淡忘（第 3 章），
hook 不會。原則：該由機器保證的事不要交給記憶。

**BOOTSTRAP（繁殖程序）**：factory repo 裡的一份出廠程序書。要為新工作長出一個 agent
時，照著走：建大腦 repo 骨架 → 派子 agent 掃描工作 repo 自動生成第一版領域知識 →
接上 dream 排程 → workspace 接線（指標、設定、hooks）→ 驗收。每個 instance 生下來就
繼承全部方法論與教訓——這就是「factory」之名的由來。

# 第三部：坑的圖鑑

> 這一部是這本書最值錢的部分。每個坑都真實發生過，格式統一：癥狀 → 根因 → 修法 →
> 一般化教訓。

## 第 10 章　無聲死亡的排程

**癥狀**：dream pipeline 停止運作，無人察覺。發生了**三次**：工作機 lis 停了三週
（2026-06-08 → 07-01）；jac 只在 7/12 手動跑過一次後停了 34 天；iic 從建立起根本沒跑過。

**根因**（一次比一次深）：
- 排程設定檔硬編了某台機器的絕對路徑，換機器後排程「安靜地不存在」。
- 排程器本身會無聲卸載（macOS launchd 在某些系統事件後掉載入），而 pipeline 的存活
  沒有獨立監控——監控者不能只依附在被監控者身上。
- 最根本的：自動化的活性（liveness）被假設而非驗證。「裝好了」≠「在跑」。

**修法**：安裝腳本改為從所在目錄自動導出所有路徑與名稱（消滅硬編）；session 開場的
強制 staleness check（記憶目錄超過三天沒更新 → 先警告再工作）；dream log 缺席本身
成為警報。

**一般化教訓**：這其實是 factory 教訓庫裡「通道活性是第三方狀態，要 round-trip 驗證」
的同族——你的註冊動作成功 ≠ 對方那邊還活著。同一個坑在 Telegram bot 上以「bot 失聰
一個月、被用戶發現兩次」的形式踩過，才被蒸餾成通用紀律。

## 第 11 章　隱形的帳單

**癥狀**：夜間自動任務悄悄消耗昂貴的模型額度。

**根因**：headless 模式（`claude -p`，無人值守跑一段指令）有兩個不明顯的預設行為：
1. **繼承使用者的預設模型**。Leo 的互動預設是最貴的 Fable——於是 jac 的 7/12 dream、
   以及 general-personal-agent **每一晚**的 dream，都在用 Fable 額度跑本該用普通模型的
   整理工作。直到 2026-08-15 audit 才發現。
2. **預設載入整套環境**。實測一個字的 prompt 也可能吃 ~170K token/呼叫，大宗是工具
   schema 與各種動態 context。純文字任務要顯式關閉，可省約 30 倍。

**修法**：所有排程腳本顯式 `--model`（一行）；純文字工作用極簡旗標組合；用
`--output-format json` 讀 usage 欄位逐項驗證省了什麼。

**一般化教訓**：預設值是有立場的。無人值守的自動化，每一個依賴預設的參數都要顯式化。

## 第 12 章　兩套真相

同一資訊存在兩個地方，就必然有一天互相矛盾。這個系統以三種形式踩過：

1. **Skill drift**：工作流程有兩份描述——舊版引用一套已退役 Python 服務的 39 個工具
   呼叫，新版是檔案操作。舊版還在教「直接寫 LTM」（違反第 7 章鐵律）。修法：舊檔改成
   指向新檔的薄殼，歷史註記「勿用」。
2. **本機落後遠端 48 個 commit**：個人機的 factory checkout 太久沒 pull，工作機這段時間
   推了幾十條教訓上去。後果：整段「系統歷來只產出 3 條教訓」的分析完全失真；更戲劇化的
   是修好後 push 時遠端**又**前進了，第一次 push 被拒。同一天兩次自證。修法升格為
   **最高指導原則 0：Sync With the World First**——任何分析動工前，fetch 所有會碰的
   repo、刷新所有引用的外部狀態。
3. **原生記憶 vs 自建記憶**（詳見第 13 章）。

**一般化教訓**：single source of truth 不是美學，是正確性的前提。允許第二份 copy 存在
的那一刻，就要同時設計同步機制，否則就是在排程一次未來的誤診。

## 第 13 章　寫錯地方的記憶

**案例一：影子記憶**。Claude Code 2026 年起內建「auto memory」：以 session 所在目錄為
單位，自動累積記憶檔。這跟自建記憶系統並存的結果，實測抓到兩種實害：同一條教訓存在
**三份**（原生層、instance 層、factory 層）；以及一條 Leo 的行為規則只被原生層抓到、
自建系統（dream、LTM）完全看不見——兩套記憶各自演化，互不知情。

**決策**（2026-08-15，經比較後拍板）：自建 dream 在每個維度上 ≥ 原生（有對帳、有衰減、
有跨 instance 傳播、資料在自己的 git 裡、不受供應商政策變動影響；原生的「Auto Dream」
整理機制甚至不在官方文件裡），因此**有自建記憶系統的 repo 一律關閉原生 auto memory**，
沒有自建系統的一般專案才留用。這是「依賴供應商便利 vs 掌控自己資料」的典型取捨，
選了後者。

**案例二：孤兒記憶**。工作 repo 缺了那行指回大腦的指標，某三天的工作 session 在工作
repo 裡開起來，把一次重要事故（wave-7）的完整記憶寫進了**產品 repo**——dream 在大腦
repo 裡夜夜運轉，從沒見過這批檔案。事後 dream log 還留下一句無辜的註記：「wave-7 沒有
STM」。修法：補指標、把記憶遷回、時間戳調整讓下一晚的 dream 撿到。

**一般化教訓**：記憶系統的第一原則是**單一記錄系統（single system of record）**；
第二原則是每個入口（每個可能開 session 的目錄）都要接線回它。

# 第四部：量測——2026-08-15 我們做了什麼

> 前三部的系統再精巧，都回答不了一個問題：「**它有進步嗎？你怎麼知道？**」
> 2026-08-15 之前，誠實的答案是：不知道。量測腳本只存在於工作機、個人機兩個 instance
> 的排程從沒跑起來、而唯一的「進步證據」是教訓庫變長了——但教訓庫變長不等於行為變好
> （第 4 章的 ETH Zurich 研究正是警告這一點）。這一天補上了整個量測層。

## 第 14 章　「有進步嗎」是可以測的

不能靠感覺。最有力的警世研究：METR 的隨機對照試驗讓資深開源工程師用 AI 工具做真實任務，
**開發者自估快了 20%，碼表實測慢了 19%**。自我感覺與現實可以相差四十個百分點。

所以這天建立的量測全部避開主觀判斷，四條互相獨立的曲線：

1. **私有回歸題庫（regression suite）**：從自己過去的真實失敗出題（「這個排程現在幾點
   跑」「改評分 prompt 後要做什麼才算完成」），答案用機械規則（regex）判定，不用 AI 當
   裁判。每月重跑，出現 `REGRESSED` 就是系統在自己喊退步。原則照 Anthropic 官方 evals
   指南：20–50 題起步、驗結果不驗過程的自述、pass^k 處理隨機性。
2. **行為遙測**：從 session 記錄檔自動計算——人工介入次數、打斷次數、最長連續自主
   工具呼叫、自動核准比例。這些是「它需要我更少了嗎」的直接訊號，Anthropic 自己就用
   同款指標量測 agent 自主性。
3. **程式碼存活率**：agent 寫的程式碼 30 天後還有多少活著（git blame 計算）、被 revert
   幾次。GitClear 對 6 億 commit 的縱向分析顯示 AI 時代 code churn 翻倍——存活率是
   品質的靈敏指標。首次測量：64.2%（低於成熟專案的 ~85%，但高速迭代期 + 零 revert，
   判定為基線而非警報）。
4. **信心度趨勢**：復盤時的 1–5 自評，聚合成時間序列（自評不可信，但自評的**趨勢**
   配合其他三條曲線交叉驗證有價值）。

**資料來源**：METR, *Measuring the Impact of Early-2025 AI on Experienced Open-Source
Developer Productivity*（arXiv:2507.09089, 2025）；Anthropic, *Demystifying evals for AI
agents*（anthropic.com/engineering, 2026-01）與 *Measuring AI agent autonomy in practice*
（2026-02）；GitClear, *AI Code Quality & Maintainability Gap*（gitclear.com, 2026）。

## 第 15 章　Ablation：把記憶拔掉再考一次

量測記憶系統最直接的實驗：**同一套題目考兩次，一次帶記憶、一次把記憶目錄清空**
（用 git worktree 做出乾淨副本，角色設定保留、只拔記憶層）。差值就是記憶系統的貢獻——
如果沒有差值，那每晚的 dream 就是在燒電。

2026-08-15 的首次實測（模型 opus，兩個 instance）：

- **iic：帶記憶 87.5% vs 拔記憶 75%（+12.5 個百分點）**。決定性的一題：「GCP 專案 id
  是什麼」——正確答案是 `industy-intel`（一個少了 r 的歷史 typo），這種「不可推斷的
  事實」正是記憶存在的理由，拔掉記憶的那組直接答錯。
- 另一題兩組都答對，但帶記憶組用**一半的 token 與一半的時間**。這印證了 2026 年對照
  研究的結論：**記憶的收益經常體現在成本與回合數，而不是成功率**——量測若只看對錯，
  會低估記憶的價值。
- **jac：兩組打平**——因為題目多數能從常駐的角色設定檔答出。這是量測系統的自我修正
  功能：它連「你的題庫出得不夠刁」都測得出來。

**資料來源**：Stompy 記憶對照實驗（2026-03：成功率無差、成本 -22~32%、回合 -28~40%）；
ablation 方法論——Voyager 技能庫消融實驗（Wang et al., arXiv:2305.16291, 2023：拔掉
技能庫慢 15 倍）。

## 第 16 章　一場誤診的解剖：先量測你的量測工具

這是全書最重要的一章，因為它記錄的是**量測系統自己犯錯、然後被抓到**的完整過程。

**第一幕**：baseline 顯示兩題「答案明明白白寫在長期記憶裡」的題目掛了。手動重跑，
agent 答得完美。診斷：「檢索是非確定性的——記憶在，但取用是機率性的」。這個診斷聽起來
非常合理，還有 2026 年的 faithfulness 文獻背書（agent 經常無視自己的濃縮經驗）。

**第二幕**：針對「不穩定」做了一輪修復（強制 grep 規則、索引加標籤、檢索觸發詞），
重測。結果**更糟**：0/6 全掛。合理的診斷不會產生這種結果。

**第三幕**：真相。這台機器沒裝 PyYAML，測驗腳本落到一個備援解析器，它有兩個 bug：
regex 裡的 `\.` 沒被還原（於是判分規則變成一個**永遠匹配不到的模式**）、含逗號的
pattern 被從中切斷。**那兩題從第一天起就不可能被判對**——所謂「檢索不穩定」，是裁判
瞎了，不是考生笨。而「手動重跑通過」的假象，是因為手動重跑時用人眼看答案，沒有經過
那個壞掉的裁判。

**修法與制度化**：
- `--check` 自測：每題入庫前，拿一段手寫的正確答案餵給判分器，判分器判「錯」就是
  判分器壞了。零 API 成本。17 題全部驗證。
- 判分失敗時自動保存 agent 的原始回答——沒有原始輸出的診斷就是猜測。
- 修好裁判後重測：兩題 **k=3 全過**。「檢索不穩定」的診斷正式撤回。

**一般化教訓**（已寫進規格）：**在宣稱被測系統有問題之前，先驗證量測系統本身**。
測驗學裡這叫效度（validity）；工程裡這叫「先校準儀器」。AI agent 的世界裡它格外重要，
因為 agent 的輸出是自然語言——判分器對語言形式的任何脆弱假設，都會變成無聲的假陰性。

## 第 17 章　教訓為何被無視，如何讓它生效

裁判修好之後，題庫裡剩下一題真正的失敗，而它揭開的問題比前面全部都深。

**Canary 測試**：在題庫裡放「測 agent 是否遵守全域教訓」的題目，像礦坑裡的金絲雀。
其中一題問：「我剛批次更新了幾百筆資料，接下來怎麼驗證？」教訓庫裡白紙黑字：
「驗證 100% 的列，絕不抽查」。

**結果（k=3，三次全掛）**：agent 的回答本身相當出色——主動查了資料庫完整性、抓到
沒做備份、設計了分層驗證——**但它從頭到尾沒去讀教訓庫**（儘管指示檔明寫「動資料庫前
先讀」），還建議「抽樣檢查」，正面違反教訓。這就是 2026 年系統性研究的結論在自家系統
的重演：**agent 可靠地使用原始經驗，卻經常無視或誤讀濃縮過的經驗**；Vercel 的評測也
發現該被觸發的技能檔在 56% 的場合根本沒被載入。「把教訓寫下來」和「教訓在關鍵時刻
被想起」之間有一道實證的鴻溝。

**修法：三層互補（當天全部實作並驗收）**：

1. **常駐層（hot lessons）**：最高風險的六條紀律直接放進每次都會載入的角色設定檔，
   由 dream 每晚與教訓庫同步，上限八條——因為第 3 章的指令天花板，這一層是稀缺資源，
   升降級要人拍板。
2. **攔截層（hook）**：資料庫寫入、部署類指令第一次出現時，確定性地擋下並要求先讀
   對應教訓章節。不依賴模型「記得」。
3. **按需層（sparse injection）**：正式任務開工時，用任務關鍵字檢索教訓庫、只注入
   最相關的 **1–2 條**。不是越多越好——實測檢索 1 條的效果勝過 4 條，多塞反而害
   （ReasoningBank 的 k=1 > k=4 消融）。

**驗收**：同一隻金絲雀，修復前 0/3，修復後 **3/3**；而且第一次作答只用 1 回合、
28K token（修復前每次徒勞搜尋要 4–5 回合、110–160K token）——又對又便宜。對照組
（另一 instance 的金絲雀）維持 3/3，確認沒有誤傷。

這是整套量測層建成後的**第一個完整閉環**：量測發現問題 → 定位根因 → 修復 →
同一個量測轉綠。從這一天起，「它有進步嗎」不再是信仰問題。

**資料來源**：Lin et al., *LLM Agents Are Not Always Faithful Self-Evolvers*
（arXiv:2601.22436, 2026）；Vercel, *AGENTS.md outperforms skills in our agent evals*
（vercel.com/blog, 2026）；ReasoningBank k=1 消融（arXiv:2509.25140）；hook vs 指示的
遵守度——McMillan（arXiv:2605.10039, 2026）。

# 第五部：對照與展望

## 第 18 章　Before / After：2026-08-15 那一天改變了什麼

| 維度 | 之前 | 之後 |
|---|---|---|
| 自我精進迴路 | 設計完整但個人機上實質停擺（排程未裝/已死） | 兩 instance 每晚自動 dream，錯開時段防額度互撞 |
| 「有進步嗎」 | 無法回答（量測腳本只在工作機、且只量記憶健康度） | 四條獨立曲線：回歸題庫（k=3）、行為遙測、存活率、信心趨勢；每週自動出 diff 報告 |
| 記憶的貢獻 | 信仰 | 實測 +12.5pp 正確率、一半 token（ablation） |
| 夜間任務成本 | 隱性燒 Fable 額度（含另一個系統每晚一次） | 全部顯式釘定模型 |
| 教訓的效力 | 寫了就假設會被遵守 | 金絲雀持續監測 + 三層供給機制，0/3 → 3/3 |
| 教訓生命週期 | 只加不減、無格式上限 | ≤50 字 + 適用條件、增/修/廢三種操作、來源標記（防注入） |
| 量測可信度 | 無自檢 | 判分器入庫前強制自測、失敗保存原始輸出 |
| 記錄系統 | 原生/自建雙軌並行、互不知情 | 單一記錄系統，原生層在有自建系統處關閉 |
| 世界同步 | 各機各自為政（曾落後 48 commits） | 最高指導原則 0：開工前 fetch 一切 |

## 第 19 章　界限與開放問題

誠實的收尾：這套系統現在能做到什麼、還不能做到什麼。

**已知的界限**：
- 回歸題庫 17 題，離 20–50 題的目標還有距離；且偏重「記憶檢索」型，「執行行為」型
  （真的動手改碼並驗證結果）還沒開始。
- 教訓 merge 前的 eval gate（用題庫 A/B 測一條新教訓是幫忙還是幫倒忙——GEPA 式的
  選擇壓力）已寫入規格，但要等題庫成熟才強制。
- 記憶投毒是真實威脅：研究顯示 0.1% 的毒樣本能達到 80%+ 攻擊成功率，且注入內容能偽裝
  成「經驗」在反思迴路中自我強化。目前的防線（來源標記 + 人工審核）是紙欄杆，夠用但
  不厚。
- 記憶系統的長期行為未知：有研究發現不同記憶架構的優劣排名會在第 3 週與第 9 週之間
  **反轉**（tenure crossover）——這套系統還沒活過足夠長的量測期。

**給想自建的人，最小可行版只需要四樣**：一個放記憶的 git repo、一份「什麼問題查到
哪層就停」的檢索協議、一個夜間整理排程（哪怕只是 cron + 一段 prompt）、和**從第一天
就開始的量測**（哪怕只有五道題）。這本書第三部的每一個坑，都是在沒有第四樣的時期
挖下的。

**資料來源**：GEPA 反思式提示演化（Agrawal et al., arXiv:2507.19457, ICLR 2026）；
記憶投毒——AgentPoison（arXiv:2407.12784, NeurIPS 2024）、MINJA（arXiv:2503.03704,
2025）；tenure crossover——*Ground Truth First*（arXiv:2607.21962, 2026）。

# 附錄 B　術語表（從零讀者用）

| 術語 | 白話 |
|---|---|
| LLM | 讀過海量文字、會接話的模型 |
| Agent | LLM + 工具 + 「思考→行動→觀察」迴圈 |
| Context window | 模型單次能看到的全部文字；session 的白板 |
| Token | 模型計量文字的單位，約 0.5–1 個中文字 |
| Instance | 一個工作領域專屬的 agent（大腦 repo） |
| STM / LTM | 短期記憶（每任務一檔）/ 長期記憶（蒸餾過的知識） |
| Journal | 情節記憶：每場工作的敘事記錄 |
| Dream | 夜間無人值守的記憶整理管線 |
| L4 / Ground truth | 真實世界的系統（git、ticket、資料庫）——記憶之外的最終裁判 |
| Lesson PR | instance 把通用教訓提案回 factory 的 pull request |
| Regression suite | 從過去失敗出的題庫，定期重考 |
| Ablation | 拔掉某元件再測，量它的貢獻 |
| pass^k | 連考 k 次全對才算會（對付隨機性） |
| Canary | 專測「規則是否被遵守」的哨兵題 |
| Grader | 判分器（本書中：機械規則，非 AI 裁判） |
| Hook | 工具呼叫前的確定性攔截腳本 |
| Headless | 無人值守模式（`claude -p`） |
| BOOTSTRAP | 新 instance 的出廠程序書 |
